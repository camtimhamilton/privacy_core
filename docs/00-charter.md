## 1. Что этот документ делает и чего не делает

**Делает.** Фиксирует пять решений из раздела 9 плана, выводит из них архитектурные следствия, формализует инварианты и модель данных, определяет протокол бенчмарка и бюджет задержки, пересобирает фазы так, чтобы у каждой был измеримый критерий выхода.

**Не делает.** Не содержит кода, не выбирает конкретные модели, не описывает API шлюза к внешним LLM. Это следующий документ (`docs/10-architecture.md`).

**Проверяемое утверждение плана, которое здесь уточняется.** В разделе 3 плана сказано «высокая точность при нуле ложных срабатываний» о форматных детекторах РФ. Это неточно и опасно как обещание: у контрольных сумм есть собственная вероятность ложного прохождения на случайных цифрах. Разбор — в разделе 3.5. Мы заменяем лозунг на измеримую величину: доля ложных срабатываний на корпусе чистых текстов, и называем её честно.

## 2. Пять решений и их следствия

### 2.1 Сводка решений

| № | Вопрос | Решение | Что из этого следует |
|---|---|---|---|
| Р1 | Стек ядра | Rust-ядро, биндинги Python / JS / WASM | Ядро без интерпретатора, NER как сменный провайдер, три профиля задержки, «один бинарь» достижим |
| Р2 | Лицензия и коммерция | Apache-2.0 на всё, коммерческой части нет | Границы модулей свободные, можно резать иначе; раздел «чего не умеем» становится обязательным, а не маркетинговым |
| Р3 | Аудитория v0.1 | Одиночки-разработчики | Приоритет: CLI, демо за минуту, установка `cargo install` / `pip install`, плагин редактора раньше браузера |
| Р4 | Протокол бенчмарка | Двухуровневый: Core (инварианты) + Extended (полные метрики) | Бенчмарк проектируется до детекторов; Core проходим почти всеми, Extended — поле конкуренции |
| Р5 | Контекстные утечки | Делать первыми, полноценное разрешение ссылок | Отдельный версионируемый модуль на критическом пути; фаза 0 получает ворота go/no-go |

### 2.2 Р1 — Rust-ядро с биндингами

**Следствия, которые нужно проектировать сразу:**

1. **NER не может быть обязательной зависимостью ядра.** Тяжёлая модель не влезает ни в 25 мс, ни в «один бинарь», ни в WASM-сборку разумного размера. Значит, статистический NER — сменный *провайдер* за трейтом, а ядро поставляется с рабочим форматным каскадом и без модели. Пользователь, которому нужен NER, подключает ONNX Runtime и модель сам, и получает другой профиль задержки (раздел 7).
2. **Три биндинга — три разных продукта, а не три обёртки.** Python: `pip install privacy-core`, доступ из Presidio-подобных пайплайнов. JS/Node: для прокси и CLI. WASM: для браузера, где нет файловой системы — значит, карта соответствий обязана жить в памяти и в `IndexedDB`, а не в файле на диске.
3. **Аудитория контрибьюторов сужается.** Это цена решения. Компенсация: детекторы форматов, локализации и генераторы синтетических данных выносятся в данные (декларативные правила плюс тестовые примеры), которые можно добавлять без Rust.
4. **Задержка перестаёт быть риском и становится контрактом.** Три профиля в разделе 7 — это публичные обещания с тестами в CI, а не пожелания.

**Что теряем.** Скорость разработки фаз 2 и 5. Прототип на Rust дольше, а итерации по детекции требуют пересборки. Смягчение: сменные правила выносим в конфиг и в отдельный груз (`rust-embed`) с горячей перезагрузкой — менять правила без пересборки ядра.

### 2.3 Р2 — Apache-2.0, без коммерческой части

**Следствия:**

1. Никаких искусственных границ между «открытым ядром» и «платным слоем». Модули режем по инженерной логике, а не по бизнес-логике. Это прямо снижает риск скатиться в «форк Presidio с косметикой».
2. Патентная оговорка Apache-2.0 закрывает вопрос корпоративного использования, который в анти-цели №7 назван явно.
3. **Появляется обязательство, которого нет у коммерческих конкурентов:** раздел «чего ядро не умеет» и публичная модель угроз. Без коммерческого интереса нет причин их прятать, и это становится частью позиционирования.
4. Отпадает вопрос о лицензии для данных бенчмарка — она наследует Apache-2.0, и чужие решения могут проходить бенчмарк без юридических консультаций.

**Открытый риск.** Если позже появится желание монетизировать, смена лицензии потребует согласия всех контрибьюторов. Решение принимается сейчас и осознанно: либо сразу CLA, либо оставляем как есть и не пересматриваем. См. раздел 13.

### 2.4 Р3 — одиночки-разработчики

**Следствия:**

1. Метрика успеха v0.1 — не «корпоративный пилот», а «человек поставил за минуту, увидел демо за минуту, оставил звезду или issue».
2. Демо «что ты написал / что реально ушло наружу» из фазы 6 — не витрина, а основной артефакт. Оно определяет структуру CLI: `privacy-core show` обязан печатать оба текста и таблицу подмен.
3. Командные функции (общий прокси, роли, аудит) не делаем вообще до v0.2, даже если просят.
4. Порядок интеграций из фазы 7 сохраняется, но приоритет внутри него меняется: CLI → плагин VS Code/Cursor → OpenAI-совместимый прокси → браузер → терминал.

### 2.5 Р4 — двухуровневый протокол

**Следствия:**

1. **Core-уровень проектируется до детекторов** и состоит из инвариантов, а не из процентов. Это позволяет опубликовать протокол раньше, чем собственный результат, и владеть стандартом с первого дня.
2. Extended-уровень — таблица по типам сущностей, и она соревновательная. Именно туда встают Presidio и LLM Guard.
3. Публикация всегда содержит обе части: «Core пройден / не пройден» плюс «Extended: такие-то цифры». Неудача в Core не маскируется хорошими цифрами Extended.
4. Полный протокол — в разделе 6.

### 2.6 Р5 — контекстные утечки первыми

Это самое дорогое из пяти решений, и его нужно понять до конца.

**Почему дорого.** Контекстная утечка — это свойство связного текста и истории диалога, а не отдельного токена. Детекция ссылок требует разрешения анафоры и кореференции, то есть модели уровня диалога. Значит:

- ядро перестаёт быть чистой функцией `текст → текст` и получает состояние: активные сущности сессии, историю упоминаний, граф связей;
- появляется второй проход, а с ним новый вклад в задержку;
- для русского нужен корпус с разметкой кореференции, и мы не можем обучить модель просто «на своих примерах» — иначе Extended-метрика считается на обучающем наборе, что запрещено собственным правилом фазы 3.

**Почему всё-таки стоит.** Исследовательская база для русского существует, и это меняет оценку риска с «пустое поле» на «есть датасеты, нет продукта»:

- [RuCoCo](https://ar5iv.labs.arxiv.org/html/2206.04925) — русский корпус с разметкой кореференции, 2022;
- [RU-EVAL-2019](https://www.dialog-21.ru/media/4689/budnikovzverevamaximova2019evaluatinganaphoracoreferenceresolution.pdf) — методика и метрики оценки разрешения анафоры и кореференции для русского;
- работы по нулевому субъекту и по детекции упоминаний на контекстных эмбеддингах (XLM-R, rubert).

Ни у Presidio, ни у LLM Guard, ни у Portcullis этого нет — Portcullis решает другую задачу (параллельная подстановка и доверенная среда), а не связность текста.

> **Поправка по итогам фазы 0 (16.10.2025).** Найден работающий проект [SurrogateShield](https://github.com/sherwinvishesh/SurrogateShield) (Apache-2.0), у которого есть `Relation Gate (v2)` — механизм, оставляющий место или организацию как есть, если ничто не связывает их с человеком, и подменяющий при наличии связи — а также риск-скоринг комбинаций квазиидентификаторов по таблице (индекс + дата рождения + пол и другие). То есть утверждение «не решено нигде» неверно и здесь. Что действительно остаётся незакрытым: **анафора и ссылки** («мама», «та фирма», «последний отчёт») — такого механизма у SurrogateShield нет; их риск-скоринг только предупреждает и ничего не меняет в поведении. Подробности — в [аудите фазы 0](../phase-0/01-audit.md). Отличие №3 сужается: не «контекстные утечки», а **разрешение ссылок с переписыванием текста**.

**Как ограничиваем риск — ворота в фазе 0.** **[ЗАКРЫТО]** Полный аудит выполнен, решение — **GO с сужением объёма**. Документы: [аудит контекстных утечек](../phase-0/01-articles/contextual/README.md), [решение ворот](../phase-0/01-articles/contextual/contextguard-gate.md).

**Что установил аудит:**

| Факт | Значение |
|---|---|
| Задача контекстных утечек решена где-нибудь локально на CPU? | **Нет.** Все существующие методы требуют прогона LLM на каждом шаге |
| Работы на стыке «кореференция ↔ приватность» для русского | **Не существует ни одной** |
| Лучший русский резолвер кореференции | 0.751 F1 по LEA, требует 10–45 ГБ памяти |
| Лицензии русских корпусов кореференции | **Ни одного, совместимого с Apache-2.0** (RuCoCo без лицензии, RuCoCo-2023 под CC-BY-NC-4.0) |
| Публикует ли хоть одна работа задержку в миллисекундах | **Нет ни одной** |
| Цена неполноты: при маскировке >90% явных спанов защита на уровне субъекта падает | **до 33%** (SPIA) |
| Рост утечки с длиной диалога | **до 3 раз** при переходе с 1 на 6 ходов (CIMemories Dialogue) |
| Патент US11741163B2 «Mapping of PII to a person based on natural language coreference resolution» | существует; **формула не читалась — потенциальный юридический блокер** |

**Решение: сужение задачи.** Модуль строится **не** как разрешение кореференции и **не** как детектор, а как **линковка ссылок на уже известный реестр сущностей диалога**. Вход — реплика плюс реестр; выход — для каждой ссылки идентификатор записи реестра либо «не разрешено».

Почему сужение обязательно: полное разрешение кореференции в бюджет 8 мс не влезает ни при каком известном подходе — все резолверы требуют 10–45 ГБ и десятки-сотни миллисекунд. Мы проиграли бы по определению.

**Ключевое техническое преимущество — русская морфология.** Согласование по роду, числу, падежу и одушевлённости даёт бесплатный и сильный сигнал для отсева кандидатов, которого нет у английских моделей. Это критерий A3 ворот: если он не работает, у проекта нет преимущества, и решение переходит в NO-GO.

**Архитектура (пять эшелонов):**

| Эшелон | Что делает | Бюджет |
|---|---|---|
| 0 | Инкрементальное состояние диалога: реестр сущностей с морфологическими признаками | O(1) от длины реплики, пересчёт по истории запрещён |
| 1 | Извлечение указателей: личные, притяжательные, указательные, дескриптивные («та фирма»), нулевой субъект | микросекунды |
| 2 | Скоринг кандидатов по признакам, отсев по согласованию | доли миллисекунды |
| 3 | Решение: линковка или явный отказ «не разрешено» | — |
| 4 | Риск-скоринг остаточного риска по триггеру, а не на каждый ход | **вне бюджета 8 мс** |

Правило: эшелоны 1–3 живут в 8 мс, эшелон 4 — вне их. Смешивать нельзя.

**Обязательные критерии приёмки (все пять, иначе NO-GO):**

| Критерий | Формулировка |
|---|---|
| A1 | Сужение зафиксировано письменно: формальный вход/выход и перечень того, что модуль не делает |
| A2 | Собственный замер: p95 ≤ 8 мс на реплике до 128 токенов при непустом реестре 10–50 записей. Чужих цифр не существует — оценка «правила уложатся» гипотезой и остаётся |
| A3 | Отсев по русской морфологии снимает не менее половины кандидатов до применения семантики |
| A4 | Собственный бенчмарк: русские многоходовые диалоги с разметкой, **субъект-уровневая** метрика, разбивка по длине диалога (1/3/6 ходов), лицензия Apache-2.0-совместимая |
| A5 | Юридическая чистота: прочитана формула патента US11741163B2 и зафиксирован вывод; все данные лицензионно чисты |

**Что отвергаем явно:** готовые русские резолверы (вес, задержка, лицензии); «полное разрешение кореференции»; обучение на RuCoCo и RuCoCo-2023 (лицензии несовместимы); CAMP как основу (4 синтетических сценария, один автор, чисел нет); ставку на «два раздельных контекста» как защиту — гипотеза **не подтвердилась**, работа Leaky Thoughts показывает, что трасса рассуждений утекает и является дополнительной поверхностью атаки.

**Поправка к прежней гипотезе.** «Два раздельных контекста диалога», взятые из SurrogateShield как идея защиты, **не работают** так, как предполагалось: рассуждения модели тоже утекают. Это надо учесть в модели угроз, а не только в архитектуре модуля.

**Важное уточнение объёма.** «Сделать первым» не означает «сделать всё сразу». Осознанно разделяем:

- **v0.1 — ContextGuard-L (линковка):** находит указатели («мама», «та фирма», «последний отчёт», нулевой субъект), связывает каждый с записью реестра сущностей сессии или отвечает «не разрешено». Это не разрешение кореференции, а линковка на известный реестр — см. решение ворот выше.
- **v0.2 — ContextGuard-R (переписывание):** собственно замена ссылки в наружном тексте так, чтобы модель понимала, о ком речь, с сохранением связности.
- **Дальше — риск-скоринг:** калиброванная оценка остаточного риска по образцу k-анонимности, вне бюджета 8 мс, по триггеру, а не на каждый ход.

Причина разделения: ContextGuard-R меняет текст, который видит внешняя модель, и при неудаче ухудшает ответ. Это тот же класс ошибок, что и ложная подмена, и требует отдельного класса тестов на сохранение смысла. Смешивать его с детекцией в одном релизе — способ не выпустить ничего.

### 2.7 Что в плане нужно поправить

Две фактические неточности, обе влияют на позиционирование.

| В плане | Как на самом деле | Что меняем в тексте |
|---|---|---|
| «Portcullis — параллельная подстановка, 96x быстрее предшественников» | 96x — ускорение против Hide-and-Seek на нагрузке маскирования/снятия маски; подстановка там параллельная, но основа — доверенная среда с аттестацией | Формулируем как «96x на маскировании против Hide-and-Seek, плюс аттестация среды» |
| «Форматные детекторы РФ дают высокую точность при нуле ложных срабатываний» | Контрольная сумма снижает, но не обнуляет ложные прохождения | Заменяем на измеряемую долю ложных срабатываний на чистом корпусе (раздел 3.5) |
| «SurrogateShield: 96.87% F1, сохранение смысла 94.85% против 81.59%, накладные 25.89 мс» | Эти числа — из **препринта, описывающего более старую систему**. В препринте: 3 стадии, 22 типа, Faker. В текущем коде версии 1.9.0: **6 стадий, 13 типов, своя генерация, другой бенчмарк**. Числа несопоставимы | Цитируем числа из их опубликованного бенчмарка `test-3` (утечка 0.73%), а не из препринта. Про сам препринт указываем, что это препринт без рецензирования и цитирований |
| «SurrogateShield решает контекстные утечки» | Механизмы существуют, но: `ContextGuard` **выключен по умолчанию**; `Relation Gate` при выключении **снижает** утечку (0.65% против 0.82%), то есть борется с ложными правками; риск-скоринг квазиидентификаторов — таблица из 10 жёстких комбинаций, работающая **только на запись в журнал** | Формулируем точно: решена привязка места и организации к человеку как эвристика; риск-скоринга и анафоры нет |
| «Накладные 25.89 мс» как задержка | В их данных **p50 = 43.5 мс, а p95 = 204 мс** (в 4.7 раза выше медианы) | Публикуем p50, p95 и максимум; медиана только как медиана |
| «Контекстные утечки не решены нигде» (вывод раздела 2.6) | **Анафора и ссылки не реализованы нигде** — это подтверждено поиском по коду SurrogateShield (ноль совпадений). А привязка места и семантические комбинации частично проработаны | Отличие №3 сужается до **разрешения ссылок с переписыванием текста**, и это подтверждено как чистая ниша |

## 3. Инварианты ядра

Формулируются как свойства, проверяемые машиной, а не как намерения. Каждому инварианту соответствует набор тестов и, где возможно, свойство в property-based тестировании.

### 3.1 Базовые четыре из плана

**I1 — Ни одно исходное значение не покидает устройство.**
Для любого входа `T` и любого выхода наружу `E`: множество исходных значений, входящих в `E`, пусто. Проверка: тест сравнивает `E` с исходными спанами по всем нормализациям (регистр, пробелы, дефисы, транслит, юникод-гомоглифы, цифры словами).

**I2 — История диалога наружу не накапливает исходные данные.**
Третья реплика сессии не может содержать исходное значение, даже если оно было названо в первой и больше не повторялось. Проверка: сессионный тест на всей истории, а не на одном сообщении.

**I3 — Восстановление не искажает посторонний текст.**
Если подстановка `S` встретилась в ответе не как результат нашей подстановки (совпадение, цитата, часть слова), восстановление её не трогает. Проверка: набор ответов-приманок, где фейк встречается в чуждом контексте.

**I4 — Любой сбой детекции не приводит к отправке исходного текста (fail-closed).**
Паника в детекторе, таймаут провайдера, битая карта, отказ ONNX Runtime — наружу не уходит ничего либо уходит сообщение об ошибке. Проверка: инъекция сбоев в каждый узел каскада.

### 3.2 Инварианты, которые добавляем

**I5 — Согласованность подмен внутри сессии.**
Одно исходное значение → одна подмена на всю сессию. Разные значения → разные подмены. Проверка: коллизионный тест на сессии с однотипными сущностями (два Ивана Ивановича, два ИНН с общим префиксом).

**I6 — Обратимость не зависит от детектора.**
Восстановление работает по карте соответствий, а не повторной детекцией. Иначе невосстановимая сущность = потеря данных. Проверка: восстановление после принудительного отключения детекторов.

**I7 — Композиция политик сужается, а не расширяется.**
Объединение двух политик даёт множество подмен не меньше, чем каждая по отдельности. Нельзя «случайно ослабить» приватность, добавив политику. Проверка: property-based тест на решётке политик.

**I8 — Контракт профиля задержки соблюдается или нарушение объявляется.**
Превышение p95 в профиле Fast — ошибка сборки CI, а не предупреждение. В Balanced и Max — предупреждение с публикацией цифры.

**I9 — Ключ карты не хранится рядом с картой.**
Карта на диске зашифрована; ключ — в системном хранилище (Keychain, Secret Service, DPAPI) либо передаётся вызывающей стороной. В WASM ключ живёт только в памяти вкладки.

**I10 — Разметка ответа не ослабляет I1–I3.**
Логи, телеметрия, сообщения об ошибках, отладочный вывод не содержат исходных значений. Проверка: сканер логов на тестовом прогоне.

### 3.3 Что инвариантами не является

Честно отделяем: **защита от деанонимизации через комбинацию признаков не является инвариантом**, потому что она зависит от возможностей противника и объёма контекста, а не от нашего кода. Это цель с метрикой (раздел 6), а не свойство. Обещать инвариантом то, что зависит от внешней модели, — способ потерять доверие при первом разборе.

### 3.4 Fail-closed и его предел

I4 звучит абсолютно, но у него есть граница, которую нужно проговорить: если детектор сломан, а политика разрешает «пропустить текст при ошибке», то I4 нарушается по определению. Поэтому в модели данных есть отдельное поле поведения при сбое, и **значение по умолчанию — блокировать отправку**, а не пропускать. Режим «пропустить при сбое» существует только как явный opt-in с предупреждением.

### 3.5 Честная формулировка про контрольные суммы

Замена лозунга «ноль ложных срабатываний» на измеримую величину.

Для случайной строки цифр правильной длины вероятность пройти контрольную сумму ИНН — примерно 1/11, СНИЛС — около 1/100 плюс особые случаи, ОГРН — 1/11. Это значит, что на корпусе чистых текстов, насыщенном цифрами (таблицы, логи, идентификаторы заказов), форматный каскад будет срабатывать ложно. Полностью это лечится только вторым признаком: контекстная метка («ИНН», «плательщик», позиция в форме) или соседство с другими реквизитами.

Поэтому:

- вводим два уровня уверенности: `checksum_only` и `checksum_plus_context`; подменяем оба, но помечаем по-разному;
- метрика `FP(clean)` — доля ложных срабатываний на корпусе чистых текстов — становится обязательной колонкой Extended и публикуется вместе с полнотой;
- целимся в `FP(clean) ≤ 0.1%` документов, а не в ноль. Ноль в этой метрике недостижим и не должен заявляться.

Замеренные вероятности прохождения случайных цифр по типам, следствия для разрешения подмены и список типов с обязательным контекстом — в [реестре типов сущностей](20-entity-registry.md). Там же зафиксировано, что паспорт РФ не имеет контрольной суммы и без контекстной метки подменяться не должен вообще.

## 4. Что такое ядро и где его граница

### 4.1 Определение

> **Ядро `privacy-core`** — самостоятельная библиотека с версией, которая получает текст и политику, возвращает обезличенный текст, карту соответствий и отчёт, умеет обратное превращение по карте, не знает ничего о LLM-оркестрации, не выполняет сетевых вызовов и не имеет обязательных зависимостей от ML-моделей.

Три запрета вытекают из определения и проверяются в CI:

| Запрет | Как проверяется |
|---|---|
| Нет сетевых вызовов | Ядро не линкует HTTP-клиентов; тест падает при попытке соединения |
| Нет обязательной ML-зависимости | Сборка без фич `ner-onnx` даёт рабочий артефакт и проходит Core-уровень бенчмарка |
| Нет знания о шлюзе и провайдерах | В ядре нет поля «модель», «endpoint», «провайдер»; тест на отсутствие символов |

### 4.2 Границы: кто что делает

| Задача | Ядро | Шлюз | Обвязка |
|---|---|---|---|
| Детекция сущностей | да | — | — |
| Генерация подмен | да | — | — |
| Карта соответствий и её шифрование | да | — | — |
| Восстановление ответа | да | вызывает | — |
| Политики строгости | да | выбирает | настраивает |
| Раздельные контексты диалога (отображаемый/наружный) | частично: состояние сессии | да | — |
| Инвариант «наружу только подменённое» | гарантирует API | обеспечивает маршрутизацией | — |
| Логи цены запросов | — | да | показывает |
| Сеть, ретраи, стриминг | — | да | — |
| Захват контекста из редактора/браузера | — | — | да |

Ядро знает о сессии ровно столько, сколько нужно для I2 и I5: активные сущности и их подмены. Оно не знает, куда уходит текст.

### 4.3 Версионирование и контракт

- Семантическое версионирование. Ломающее изменение поведения детекции (сдвиг результатов на регрессионном наборе) — минорная версия с публикацией дельты, а не патч.
- Ядро публикует `VERSION` и `PROTOCOL_VERSION`. Бенчмарк проверяет совместимость протокола, а не только версию решения.
- У каждого модуля (форматный каскад, NER-провайдер, ContextGuard, генератор подмен) своя версия и свой отчёт. Это требование из плана: приватность измерима отдельно, а не «в составе прокси».

### 4.4 Каскад детекции

| Каскад | Что делает | Зависимости | Уверенность |
|---|---|---|---|
| L0 Форматный | Регулярные выражения + контрольные суммы + структурная проверка | Нет | `checksum_only` |
| L1 Контекстный | Метки полей, соседство реквизитов, шаблоны документов | Нет | повышает до `checksum_plus_context` |
| L2 Статистический | NER по провайдеру (ONNX или внешний) | Опционально | `model` |
| L3 Диалоговый | Ссылки, анафора, активные сущности сессии (ContextGuard-D) | Опционально | `contextual` |

Правило: каскады не отменяют друг друга, а только повышают уверенность. Отдельный каскад можно отключить политикой, но понижение уверенности сущности не происходит молча — оно попадает в отчёт.

## 5. Модель данных и жизненный цикл

### 5.1 Основные типы

```
Session
  id: SessionId
  policy: Policy
  created_at: Timestamp
  active_entities: Map<EntityKey, Substitution>   // для I5
  context_state: ContextState                      // для ContextGuard

Span
  start: usize, end: usize                         // байтовые границы в UTF-8
  surface: String                                  // как встретилось в тексте
  entity_type: EntityType
  confidence: Confidence
  cascade: L0 | L1 | L2 | L3
  rule_id: RuleId | None
  checksum: Valid | Invalid | NotApplicable

EntityType
  id: String                                       // ru.inn, ru.snils, en.email, ...
  jurisdiction: String                             // ru, kz, by, intl
  validators: Vec<ValidatorId>
  requires_context: bool

Confidence
  level: checksum_only | checksum_plus_context | model | contextual
  score: f32 | None

Substitution
  entity_key: EntityKey                            // нормализованное исходное значение
  surrogate: String                                // то, что уходит наружу
  kind: similar_fake | placeholder | category_label
  generator_id: GeneratorId
  version: u32

MappingEntry
  entity_key: EntityKey                            // хэш + шифртекст, не открытый текст
  surrogate: String
  entity_type: EntityType.id
  created_at: Timestamp

AnonymizedText
  text: String
  mapping_id: MappingId
  report: Report                                   // без исходных значений

RestoreResult
  text: String
  restored: usize
  unresolved: Vec<UnresolvedPlaceholder>           // для метрики невосстановленных
  ambiguous: Vec<Ambiguity>                        // случай I3
```

### 5.2 Нормализация и ключ сущности

`EntityKey` считается по нормализованной форме, иначе I5 нарушается на «ИНН 7707083893» против «7707083893». Нормализация: Unicode NFC, свёртка регистра, удаление разделителей внутри числовых типов, приведение ё/е для имён. Нормализация — часть публичного контракта: изменение нормализации ломает совместимость карт.

Ключ хранится как `HMAC(key_device, normalized)` плюс шифртекст исходного значения. Открытый текст исходного значения на диск не пишется — тогда утечка файла карты без ключа не даёт данных (I9).

### 5.3 Жизненный цикл сессии

| Шаг | Действие | Что проверяем |
|---|---|---|
| 1 | Создание сессии, выбор политики, генерация ключа карты | I7, I9 |
| 2 | Детекция каскадами L0→L3 | I4, FP(clean) |
| 3 | Назначение подмен с учётом `active_entities` | I5 |
| 4 | Формирование наружного текста и обновление состояния сессии | I1, I2 |
| 5 | Ответ модели восстанавливается по карте | I3, I6 |
| 6 | Отчёт и метрики | I10 |
| 7 | Закрытие сессии: карта либо удаляется, либо шифруется долговременно | I9 |

### 5.4 Генерация подмен

> **Обновлено по итогам фазы 0.** Полный юридический разбор — в [отчёте по нормативным требованиям](../phase-0/05-legal/README.md), матрица «норма против функции ядра» — в [матрице соответствия](../phase-0/05-legal/compliance-matrix.md).

**Обязательный набор режимов.** Приказ Роскомнадзора № 140 от 19.06.2025 задаёт **закрытый** перечень методов (приложение № 2). Из них к обработке одного текста или диалога применимы пять, и все пять ядро обязано поддерживать:

| Режим | Метод по приказу № 140 | Что делает |
|---|---|---|
| `identifier` | п. 2–3, введение идентификаторов | Замена на код или номер с ключом соответствия, хранимым **отдельно** и не передаваемым третьим лицам |
| `generalize` | п. 9 пп. 1, изменение атрибутов | Округление, среднее, порог, укрупнение значения |
| `mask` | п. 9 пп. 2, изменение атрибутов | Условные знаковые обозначения, в том числе `*` |
| `distort` | п. 8, искажение атрибутов | Добавление препятствующей информации и (или) случайных значений, включая сдвиг числа |
| `delete` | п. 6–7, удаление атрибутов | Полное удаление спана вместо замены |

Три метода — **перемешивание** (п. 10), **декомпозиция** (п. 11) и **преобразование** (п. 12) — требуют массива записей, а не одного диалога. Они объявляются неприменимыми, и это фиксируется в отчёте явно: иначе проверяющий сочтёт обязательные методы нереализованными.

**Два режима вместо одного.** Прежнее деление на три вида заменяется делением на два юридических режима плюс набор методов:

- **Режим нормативного соответствия** (`ru-140`) — метод `identifier`, то есть `placeholder`. Это метод с наиболее прямым нормативным соответствием.
- **Режим максимальной полезности** (`utility`) — метод `similar_fake`. Остаётся нашим основным продуктовым режимом, но не по умолчанию в юридическом режиме.

Причина разделения: норма п. 9 пп. 3 требует «случайные значения атрибутов персональных данных, **не относящихся к субъекту**». Наш `similar_fake` детерминирован от seed и **сохраняет распределение** — то есть может коррелировать с субъектом (регион, префикс оператора). Это не нарушение, но требует явного обоснования оператором, и об этом нельзя умалчивать. Отчёт помечает, какой метод применён к каждому спану.

**Что ядро обязано запретить, а не подменять.** Обезличивание персональных данных специальных категорий (ч. 1 ст. 10 152-ФЗ — «не допускается») не выполняется: отправка блокируется. Это поведение по умолчанию, и оно согласуется с инвариантом I4 (fail-closed).

Требования к `similar_fake`, проверяемые тестами:

1. Форматная валидность: фейковый ИНН проходит контрольную сумму, фейковый телефон — разбор по шаблону.
2. Отсутствие коллизий: фейк не совпадает ни с одной реальной сущностью сессии и не совпадает с другим фейком (I5). Отдельно проверяется **биекция** карты — требование ГОСТ Р 71674-2024 п. 5.4.1.
3. Правдоподобие: сохранение распределения по регионам, годам, префиксам операторов.
4. Детерминированность от seed: одна и та же сессия при том же seed даёт те же подмены — иначе невозможно воспроизвести инцидент. В отчёте указывается, что подмена псевдослучайна и детерминирована алгоритмом.
5. Обратимость: восстановление однозначно, даже если фейк встретился в тексте ответа дважды.

**Что нужно добавить в модель данных (следствие юридического разбора):**

| Артефакт | Зачем | Основание |
|---|---|---|
| Поле «метод» у каждой подмены | Отчёт обязан показывать, какой метод применён к каждому спану | прил. № 2, п. 1 пп. 7 прил. № 1 |
| `Justification` — оценка достаточности по категориям субъектов, категориям данных и правовым основаниям | Обязательный артефакт, которого у ядра сейчас нет | п. 1 пп. 3 прил. № 1 |
| Экспортируемый протокол с явным вердиктом | Требование ГОСТ Р 71674-2024 п. 6.5 | ГОСТ |
| Срок жизни карты (TTL) | Хранение не дольше целей обработки | п. 7 ч. 1 ст. 5 152-ФЗ |
| Шаблон описания обезличивания из 6 пунктов | ГОСТ даёт готовый образец | ГОСТ Р 71674-2024 п. 5.5 |

**Чего ядро не должно обещать.** Обратимая псевдонимизация **не** переводит обработку в режим, освобождающий от согласия (п. 9 ч. 1 ст. 6 152-ФЗ), и **не** применима для составов данных по ст. 13.1 и постановлению Правительства РФ от 01.08.2025 № 1154, которое требует **необратимости**. Формулировка для документации:

> `privacy-core` реализует обратимое обезличивание в смысле п. 9 ст. 3 152-ФЗ и методов, утверждённых приказом Роскомнадзора от 19.06.2025 № 140. Ядро является технической мерой защиты по ст. 18.1 и 19 152-ФЗ и инструментом снижения идентифицирующего потенциала перед передачей данных внешним моделям. Ядро не переводит обработку в режим, освобождающий от согласия, и не применимо к режиму, требующему необратимости.

**Полезное совпадение.** Требование приказа к ключу — «хранится оператором **отдельно** и не передаётся третьим лицам» — это ровно наш инвариант I9 (ключ не рядом с картой). Юридическое требование и требование безопасности здесь совпадают, что редкость.

**Нормативное обоснование Adversarial-уровня бенчмарка.** Методические рекомендации Роскомнадзора от 13.12.2013 дают единственную в РФ формализованную систему критериев оценки: обратимость, вариативность, изменяемость, **стойкость к атакам идентификации**, возможность косвенного деобезличивания. Там же прямо назван k-anonymity как пример заданного уровня анонимности. Это значит, что наш уровень атак — не научное украшение, а нормативно ожидаемая часть оценки.

**Чего фаза 0 не проверила (юридически значимо):** актуальный перечень стран с адекватной защитой данных; полный текст ФЗ от 26.07.2026 № 243-ФЗ; первоисточник методических рекомендаций 2013 года; практика по API-вызовам внешних моделей (вывод про локализацию опирается на толкование, а не на разъяснение регулятора). Эти пункты нельзя считать решёнными.

## 6. Бенчмарк как трёхуровневая система

### 6.1 Уровни

| Уровень | Что проверяет | Проходимость | Роль |
|---|---|---|---|
| **Core** | Инварианты I1–I6, I9 | Должны проходить почти все серьёзные решения | Порог входа, «пропуск в таблицу» |
| **Extended** | Полнота по типам, сохранение смысла, задержка, память, FP(clean) | Соревновательный | Основная таблица |
| **Adversarial** | Атаки восстановления и деанонимизации | Отдельный отчёт, не порог | Научная часть и честность |

Правило публикации: Core не пройден → решение попадает в раздел «не прошли порог» с указанием, какой именно инвариант нарушен. Хорошие цифры Extended этого не маскируют.

### 6.2 Что именно проверяет Core

| ID | Проверка | Критерий |
|---|---|---|
| C1 | Утечка исходных значений в наружном тексте | 0 на регрессионном наборе, включая нормализационные варианты (I1) |
| C2 | Накопление в истории диалога | 0 на сессиях до 20 реплик (I2) |
| C3 | Искажение постороннего текста при восстановлении | 0 (I3) |
| C4 | Поведение при сбое | Наружу не уходит исходный текст ни в одном из 8 сценариев сбоя (I4) |
| C5 | Согласованность подмен в сессии | Нет коллизий и расщеплений (I5) |
| C6 | Обратимость без детектора | 100% восстановление по карте при отключённых детекторах (I6) |
| C7 | Хранение карты | Открытый текст отсутствует в файле карты (I9) |

**Что Core не проверяет и почему.** Инварианты I7 (композиция политик) и I8 (контракт профиля задержки) не входят в Core-уровень, потому что это свойства не конечного текста, а библиотеки. Они проверяются своими механизмами: I7 — property-based тестом на решётке политик в тестах ядра, I8 — замером задержки в CI по каждому профилю. Отсутствие I7 и I8 в Core не означает, что они необязательны: провал любого из них блокирует релиз так же, как провал C1.

### 6.3 Расширенный уровень: метрики

| Метрика | Как считается | Зачем |
|---|---|---|
| Recall по типу сущности | Отдельно по каждому типу, среднее не считается | Требование плана; скрывает провалы |
| Precision по типу | Отдельно | Без неё высокая полнота достигается подменой всего |
| FP(clean) | Доля чистых документов с ложным срабатыванием | Замена лозунга «ноль ложных» |
| Доля запросов с утечкой | Запрос, где хотя бы одно исходное значение ушло наружу | Главная бизнес-метрика |
| Доля невосстановленных подмен | `unresolved / total` | Качество восстановления |
| Сохранение смысла | Отдельная модель-судья или ручная разметка, публикуется протокол | Отличие от заглушек |
| Задержка p50/p95 | По профилям, на CPU, текст 2k токенов | Контракт |
| Память RSS | По профилям | Контракт |
| Время старта | Холодный старт бинаря | Для CLI и встраивания |
| Размер WASM-бандла | Сжатый | Для браузера |
| Восстановление атакой | Adversarial-уровень | Раздел 6.5 |

### 6.4 Честность набора

Три правила, нарушение которых обесценивает весь бенчмарк:

1. **Разделение наборов.** `dev` используется при разработке детекторов, `test` — только для публикации. Пересечение по документам, а не только по строкам (иначе утечка через соседние абзацы).
2. **Регрессионный набор заморожен** и версионируется. Изменение набора — новая версия протокола, старые результаты остаются с пометкой версии.
3. **Чистый корпус обязателен.** Без него FP(clean) неизмерим, а он — половина доверия к форматным детекторам.

### 6.5 Adversarial-уровень

| Атака | Что моделируется | Метрика |
|---|---|---|
| Прямой вопрос | «Назови настоящее имя собеседника» | Доля успешных извлечений |
| Комбинация признаков | Три безобидных признака вместе идентифицируют человека | Доля успешных идентификаций на синтетических персонах |
| Инверсия фейка | Проверка фейка по внешним справочникам (валидный ИНН существует?) | Доля фейков, попадающих в реальные реестры |
| Через историю | Данные из первой реплики извлекаются в пятой | Доля успехов |
| Через формат | Восстановление по формату подмены | Обратимость фейка без карты |

Результаты Adversarial публикуются с описанием возможностей противника. Атака без описанной модели противника — не результат.

## 7. Бюджет задержки и профили

### 7.1 Три профиля вместо одной цели

Единая цель «p95 ≤ 25 мс на 2k токенов» противоречива: форматный каскад укладывается в единицы миллисекунд, статистический NER уровня transformer — нет. Поэтому контракт параметризуется.

| Профиль | Состав | p95, 2k токенов | Память | Зависимости |
|---|---|---|---|---|
| **Fast** | L0 + L1 | ≤ 5 мс | ≤ 30 МБ | Только Rust, влезает в WASM |
| **Balanced** | L0 + L1 + L2 (дистиллированный NER) + L3-D | ≤ 25 мс | ≤ 250 МБ | ONNX Runtime + модель |
| **Max** | Balanced + крупный NER + второй проход проверки | ≤ 100 мс | ≤ 700 МБ | ONNX Runtime + 2 модели |

Цели из таблицы метрик плана (≤ 50 мс для v0.1, ≤ 25 мс для «лучшего на рынке») сопоставляются с профилем Balanced. Профиль Fast публикуется отдельно и в Extended-таблице идёт отдельной строкой — это честнее, чем усреднять.

### 7.2 Разложение бюджета Balanced

| Стадия | Бюджет p95 | Примечание |
|---|---|---|
| Нормализация и токенизация | 1 мс | Unicode-графемы, без внешних зависимостей |
| L0 форматный каскад | 4 мс | Скомпилированный автомат (Aho-Corasick + regex) вместо сотни отдельных регулярок |
| L1 контекстный | 2 мс | Оконные проверки вокруг найденных спанов |
| L2 NER (ONNX) | 12 мс | 4–6 слоёв, квантование; крупная модель сюда не влезает осознанно |
| L3-D диалоговый | 8 мс | Разрешение ссылок на диалоге до 10 реплик |
| Генерация подмен | 1 мс | Предвычисленный пул + проверка коллизий |
| Сборка отчёта | 1 мс | Без аллокаций в горячем пути, где возможно |
| **Итого** | **≈ 29 мс** | Не влезает в 25 мс: L3-D уходит за контракт |

Честный вывод из бюджета: **профиль Balanced с включённым ContextGuard-D в 25 мс не укладывается.** Варианты, которые нужно выбрать в фазе 0 по итогам замера, а не заранее:

1. ContextGuard-D работает не на каждой реплике, а на сессии целиком, амортизируясь (тогда его вклад в per-request p95 ниже);
2. ContextGuard-D выносится в отдельный профиль `Balanced+Context` с контрактом 40 мс;
3. Цель p95 пересматривается до 40 мс, а публикуется с разбивкой по стадиям.

Это ровно тот случай, когда решение Р5 меняет измеримую цель проекта. Замалчивать его нельзя.

### 7.3 Поправка фазы 0: разрыв по задержке больше, чем мы думали

**[готово]** Аудит дал первый надёжный замер задержки на CPU для сопоставимой задачи. SurrogateShield, через GGML: **3 490 токенов в секунду**, то есть 0.59 с на 2 048 токенов (Ryzen 9 7900). На Raspberry Pi 5 — 360 токенов в секунду, 5.6 с.

Наша цель — 50 мс на 2 000 токенов, это 40 000 токенов в секунду. **Разрыв составляет 11–23 раза.** И он не закрывается оптимизацией модели размером 1.5 млрд параметров: разрыв структурный.

**Что из этого следует — и это главный технический вывод фазы 0:**

| Вывод | Следствие |
|---|---|
| Нейросеть в базовом режиме не влезает в цель ни в каком варианте | Профиль Fast и v0.1 строятся **только на правилах и контрольных суммах**, без трансформера вообще |
| Статистический NER — не «оптимизация потом», а другой профиль | Он живёт в Balanced и Max, где контракт задержки мягче, и там честно публикуется его вклад |
| «Отказ от тяжёлых зависимостей» из плана — не стилистика, а необходимость | Решение Р1 (Rust, без обязательного ML) подтверждено арифметикой, а не вкусом |

Это укрепляет решение Р1, но одновременно понижает ожидания: **полнота профиля Fast будет ниже**, чем у решений с нейросетью, и это надо публиковать, а не прятать.

### 7.4 Поправка фазы 0: выигрыш от похожих фейков оспаривается

**[готово]** Отличие №2 проекта — «похожие фейки сохраняют смысл лучше заглушек» — **не является доказанным фактом**. Найдено прямое возражение:

| Источник | Утверждение |
|---|---|
| SurrogateShield (самоописание) | +13.26 п.п. BERTScore от суррогатов против заглушек |
| Pasch & Cha, [PrivateNLP 2025](https://aclanthology.org/2025.privatenlp-main.3/), ACL Anthology | На трёх задачах письма: потеря качества от **простой маски** — около **1 балла из 10**. То есть заглушки почти не вредят |

Две работы противоречат друг другу по существу нашей гипотезы. Причём Pasch & Cha — рецензированная работа в воркшопе ACL, а заявление SurrogateShield — самоописание без рецензирования.

**Что это меняет.** Гипотеза «фейки лучше заглушек» перестаёт быть аксиомой и становится **задачей №1 бенчмарка**. Мы не можем вкладываться в сложный генератор подмен, не измерив сначала, даёт ли он выигрыш на русских задачах. Возможно, дешёвая маска плюс сохранение контекста даёт почти то же качество за малую долю сложности.

**Дополнительно, из того же аудита:**

| Находка | Следствие |
|---|---|
| Суррогаты создают атакуемую поверхность: атака Parrot находит **68%** утечек при случайном угадывании 8% | Пропуск детекции становится указанием на утечку. Нужен тест «наш суррогат против нашего пропуска» |
| Спановый F1 обманывает: при маскировке >90% спанов защита на **уровне субъекта** падает до 33% (SPIA) | Метрика проекта обязана быть **субъект-уровневой**, а не спановой. Это правка к разделу 6 |
| Никто не измеряет корректность **восстановленного** ответа | Свободное место, которое закрываем мы |
| Никто не проверяет, что фейк **не совпал с реальной сущностью** | Для РФ критично: ИНН и ОГРН — публичные реестровые номера. Валидная контрольная сумма не делает номер вымышленным |

## 12. Глоссарий и разграничение понятий

Разграничения нужны, потому что три разных вещи называют «приватностью», и это ведёт к спорам о цифрах.

| Термин | Значение здесь | Чем не является |
|---|---|---|
| Обезличивание | Замена исходных значений на подмены с сохранением структуры текста | Не шифрование и не удаление |
| Подмена (`substitution`) | Конкретное значение, уходящее наружу вместо исходного | Не заглушка по умолчанию: по умолчанию похожий фейк |
| Суррогат | Синоним подмены в научных работах | — |
| Маскирование | Замена на маркер `[ИНН_1]`, режим совместимости | Не режим по умолчанию |
| Карта соответствий | Зашифрованное хранилище связи «исходное ↔ подмена» | Не лог: не содержит открытого текста |
| Утечка | Любое исходное значение в наружном тексте, включая накопленное в истории | Не только явная отправка |
| Восстановление | Обратная замена в ответе модели | Не повторная детекция |
| Деанонимизация | Восстановление личности по комбинации признаков, включая безобидные | Не взлом карты |
| Профиль | Набор каскадов с контрактом задержки и памяти | Не режим строгости политики |
| Отображаемый контекст | То, что видит пользователь, с исходными данными | Не то же, что наружный |
| Наружный контекст | То, что уходит внешней модели, только с подменами | — |
