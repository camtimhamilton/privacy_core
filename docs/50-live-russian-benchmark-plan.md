# Живой русский набор для бенчмарка: варианты и рекомендация

**Дата:** 16.10.2026
**Задача:** найти, откуда взять **живой** русский текст для бенчмарка, потому что мерить на синтетике нельзя
**Основание:** замер из [находок после фазы 1](40-findings-after-phase-1.md) — у лидера 0.73% на вставленных значениях и **33.66%** на живых, штраф в 46 раз

---

## 1. Почему это узкое место всего проекта

Все русские наборы с персональными данными, которые мы нашли в фазе 0, **синтетические**: 115 409 строк, 24 типа, включая ИНН и паспорт — но сгенерированные машиной.

Этого мало. Замер выше показывает: решение, обученное и проверенное на синтетике, на живых сообщениях людей теряет в разы. Причина простая: генератор пишет «Уважаемый Иван Петрович, прошу подтвердить», а человек пишет «иван п. скинь адрес плз». Детектор, настроенный на первое, второе не находит.

**Значит, нужен живой текст.** Он нужен не как источник персональных данных, а как **носитель**: живая фраза, в которую мы вставим выдуманные значения точными правками. Тогда скорер точно знает, что требовалось скрыть, — а натуральность фразы настоящая.

---

## 2. Найденные источники

### 2.1 Русский корпус IT-сообщества (RICC)

| Свойство | Значение | Проверено |
|---|---|---|
| Где | [github.com/wwewtech/russian-it-community-corpus](https://github.com/wwewtech/russian-it-community-corpus), датасет `wwewtech/russian-it-community-corpus` на HuggingFace | HTTP 200 |
| Размер | **2 816 434 сообщения**, из них **171 500 многоходовых диалогов**, 325 700 фрагментов базы знаний | метаданные |
| История | 2017–2026 | README |
| Лицензия | **MIT** (в метаданных и в README) | HuggingFace API |
| PII | Авторы заявляют «Zero-PII Curation» и вероятностный аудит PII с доверительным интервалом 99% и оценкой **≤ 0.01%** | README, **не проверено независимо** |
| Важное | Есть **многоходовые диалоги** — это то, чего нет ни в одном другом наборе | README |

**Чем ценен именно нам.** Две вещи, которых нет больше нигде: **многоходовость** (нужна для проверки инварианта I2 и роста утечки с длиной диалога) и заявленная **очистка от персональных данных**. Если очистка действительно сделана, это законный источник живого текста, который не стыдно использовать в публичном бенчмарке.

**Оговорка.** Заявление об очистке — самоописание авторов. Независимой проверки нет. Доверять ему полностью нельзя, поэтому в плане ниже предусмотрена своя проверка.

### 2.2 Русские форумы (ruforum)

| Свойство | Значение | Проверено |
|---|---|---|
| Где | `nyuuzyou/ruforum` на HuggingFace | HTTP 200 |
| Размер | **58 112 681 сообщение**, 2010–2025 | сервер данных отдал точное число |
| Поля | `messageId`, `timestamp`, `text` | схема получена |
| Лицензия | **CC0 1.0** (общественное достояние) | HuggingFace API |
| PII | **Не очищено** — это сырые форумные сообщения | следует из способа сбора |

**Чем ценен.** Объём и разнообразие: форумы дают бытовую, неформальную, «грязную» речь — ровно тот домен, на котором детекторы ломаются.

**Чем опасен.** Там наверняка есть настоящие персональные данные: почта, телефоны, имена, ссылки. Использовать как есть — значит публиковать чужие данные, что недопустимо ни этически, ни юридически. Поэтому он годится только как **сырьё для локальной обработки**, а не как то, что мы публикуем.

### 2.3 Что не подошло

| Источник | Почему |
|---|---|
| RuTweetCorp, RuSentiTweet | Тональность твитов, домен другой, есть проблема с условиями использования |
| SentiRuEval | Новости и твиты, для диалогов не годится |
| Русские PII-наборы из фазы 0 | Синтетические — именно то, от чего мы уходим |

## 3. Главная ловушка, которую надо обойти

**Если взять живой форумный текст, он уже содержит настоящие персональные данные.** Вставка выдуманных значений поверх этого делает датасет с синтетическими метками, но **не удаляет настоящие данные**. Публикация такого бенчмарка — это публикация чужих ПДн под видом научного набора.

Это не мелочь и не формальность. Решение ниже построено именно вокруг этого.

---

## 4. Рекомендуемый план

### 4.1 Ключевое решение: не публиковать текст-носитель

Бенчмарк публикуется **не как датасет текстов, а как рецепт**:

| Что публикуем | Что не публикуем |
|---|---|
| Код отбора и очистки | Сам текст-носитель |
| Хэш заморозки и точные параметры отбора (индексы, версия корпуса) | Исходные сообщения |
| Метаданные внедрения: позиции, типы, значения-подмены | — |
| Небольшую долю, проверенную вручную (порядка 300 сообщений) | Остальное |

Почему так:
1. **Юридически чисто.** Мы не распространяем чужие данные, а лишь описываем, как воспроизвести набор из источника с открытой лицензией.
2. **Воспроизводимо.** По хэшу, версии корпуса и параметрам отбора набор собирается одной командой.
3. **Честно.** Заморозка не даёт менять набор после публикации результатов.

### 4.2 Разделение по происхождению

| Часть | Источник | Размер | Назначение |
|---|---|---|---|
| **Основной носитель** | RICC (MIT, очищен) | ~1 000 сообщений | Живая речь, минимум риска |
| **Проверенная вручную доля** | RICC | ~300 сообщений | Публикуется целиком, служит эталоном разметки |
| **Грязная речь** | ruforum (CC0) | ~200 сообщений | Проверка на неформальном тексте; только локально |
| **Чистый корпус** | RICC, сообщения без данных | ~500 сообщений | Замер FP(clean) |
| **Диалоги** | RICC, 171 500 многоходовых | ~100 диалогов по 1/3/6 ходов | Проверка I2 и роста утечки |

### 4.3 Конвейер

| Шаг | Что делаем | Кто | Время |
|---|---|---|---|
| 1 | Отбор сообщений по длине и языку, детерминированно | код | часы |
| 2 | Автоматическая очистка от настоящих ПДн имеющимися детекторами | код | часы |
| 3 | **Ручная проверка очистки** на выборке, исправление | человек | дни |
| 4 | Генерация вымышленных значений нужных типов | код | часы |
| 5 | Внедрение точными правками с записью позиций | код | часы |
| 6 | Заморозка: хэш, версия корпуса, параметры | код | часы |
| 7 | Прогон собственного протокола и публикация | код | дни |

**Шаг 3 — единственный, который нельзя автоматизировать, и он обязателен.** Это цена честности: без ручной проверки мы не знаем, что в наборе осталось.

### 4.4 Генератор вымышленных значений

Нужны значения, которые **проходят контрольные суммы** — иначе подмена неотличима от случайного мусора, а ответ модели деградирует.

Состояние:
- в фазе 0 написан генератор на Python (`phase-0/03-repos/scripts/gen_ru_checksums.py`, запускался, векторы сошлись);
- готовый генераторы в open source, который делает валидные **российские реквизиты**, не найден: Faker с локалью `ru` даёт формат **без контрольного ключа** (доказано чтением кода, запустить не удалось из-за запрета на установку пакетов);
- в Rust генератора пока нет.

**Задача фазы 2:** перенести генератор в Rust и расширить на СНИЛС, ОГРН, ОГРНИП, счёт и телефон. Это же нужно и для продуктового режима похожих подмен, поэтому работа не пропадёт.

### 4.5 Что даёт выигрыш

| Проблема | Как решается |
|---|---|
| Синтетика не переносится на живой текст | Носитель живой, выдуманы только значения |
| Нет многоходовых данных | RICC даёт 171 500 многоходовых диалогов |
| Нет замера FP(clean) | Слайс сообщений без данных |
| Нельзя публиковать чужие данные | Публикуем рецепт, а не текст |
| Подгонка под результат | Заморозка с хэшем |
| Скрывается провал на живом тексте | В протоколе оба замера обязательны: и на вставленных, и на живых значениях |

---

## 5. Чего этот план не решает

| Проблема | Остаточный риск |
|---|---|
| Заявление RICC об очистке не проверено независимо | Ручная проверка выборки снижает, но не устраняет |
| Ручная разметка — дни однообразной работы | Нужен человек, и это нельзя делегировать машине |
| Телефонный и адресный домены | Живой текст содержит адреса, но их разбор требует справочника адресов, которого у нас нет |
| Специальные категории | В форумном тексте есть медицинские и прочие чувствительные темы; их надо исключать из набора, а не размечать |
| Юридическая оценка | Это инженерный план, а не заключение о соответствии 152-ФЗ |

---

## 6. Что делать дальше, по шагам

| № | Действие | Почему сейчас |
|---|---|---|
| 1 | Загрузить RICC, проверить состав и заявленную очистку **своими детекторами** | Проверить заявление авторов, а не поверить ему |
| 2 | Отобрать 1 000 сообщений и 100 диалогов, заморозить выбор | Даёт основу для бенчмарка |
| 3 | Вручную проверить 300 сообщений на остаточные ПДн | Единственный способ узнать правду о наборе |
| 4 | Перенести генератор валидных реквизитов в Rust | Нужен и для бенчмарка, и для продуктового режима |
| 5 | Собрать чистый слайс из сообщений без данных | Замер FP(clean), которого нет ни у кого |
| 6 | Оформить протокол воспроизведения по хэшу | Чтобы результаты нельзя было подогнать |

**Оценка объёма.** Шаги 1–2 и 4 — дни работы. Шаг 3 — дни ручной работы человека. Шаг 5 — дни. То есть набор можно собрать за одну-две недели, и это дешевле, чем любая другая часть проекта, при том что от него зависят все наши будущие цифры.
