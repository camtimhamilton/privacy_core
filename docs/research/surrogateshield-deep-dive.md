### 3.2 Точный порядок внутри `run_cascade()` (18 шагов)

Из документации 📄 (сверено с кодом `pipeline.py`, функции и причины-строки существуют ✅):

| # | Шаг | Что делает |
|---|---|---|
| 1 | **PatternScan** | Все семейства регулярок; URL читаются первыми, неличные URL становятся *opaque*, чтобы внутри них ничего не маскировалось (кроме секретов в query и e-mail) |
| 2 | **Canonicaliser** | Те же шаблоны на «переписанных представлениях» текста; остаток текста маскирует все попадания |
| 3 | **EntityTrace** | spaCy на остатке текста |
| 4 | **ContextGuard или fallback** | Подтверждает пограничные сущности, либо (если выключен) оставляет те, что выше fallback-порога |
| 5 | **PIITagger + плагины** | Маршрутизация по `type_sources` и порогам на тип; возраст tagger'а обязан иметь форму возраста; места отбрасываются в service-запросе |
| 6 | **Anchor and snap** | Спаны в пределах строки, привязка к границам слов, снятие кавычек и предлогов |
| 7 | **Passes A, E, F, G, G2, O, H, B, C** | Структурные проходы (layout-правила) |
| 8 | **Opaque filter** | Убирает сущности, пересекающиеся с opaque URL |
| 9 | **Pass D** | Только GPE/LOC; отбрасывает места, которые лишь в под-клаузе вопроса |
| 10 | **Sentence frame** | Обрезка PERSON до самого имени (`trim_person`) |
| 11 | **Pass R: relation gate** | Гейт привязки к человеку (см. §4.1) |
| 12 | **Pass S: structural rules** | Layout + правила fiction/narrative |
| 13 | **Gender pass** | Слово рода, совпадающее с названным человеком, остаётся как написано (`gender_follows_name`) |
| 14 | **Overlap cut** | Частичные пересечения — по рангу источника, длине спана, позиции |
| 15 | **Quoted-back surrogates** | Суррогат из предыдущего сообщения сессии не считается PII (`quoted_back`) |
| 16 | **Quasi-identifier scoring** | Логирует рискованные комбинации |
| 17 | `pii_off` и `keep` | Помечает типы как немаскируемые |

### 3.3 Описание каждой стадии

**ServiceQuery** (`service_query.py`, 223 строки) 📄✅ — классифицирует сообщение как `none` / `service` («аптеки рядом с 1847 Alder Street») / `service_coarse` (сервис-запрос на чувствительную тему: ВИЧ, аборт, реабилитация, бездомность, иммиграция и т. п.). Определяет режим адреса и в сервис-запросе **останавливает модельные стадии от сообщения о местах**, чтобы город остался настоящим.

**PatternScan** (2 076 строк) 📄✅ — регулярки с проверками: Luhn (карты), ABA (банк. номера), IBAN mod-97, контрольная цифра VIN. Порядок: e-mail → API-ключ → credential → handle → crypto → MAC → IPv6/IPv4 → VIN → IBAN → ID → телефон (intl/US/UK/national) → карта → права США → паспорт → номер авто → карта (fallback) → SSN → банк США → DOB → возраст → слова рода → UK postcode → ZIP. Каждое попадание имеет score 1.0 (самый доверенный источник).

**Canonicaliser** (542 строки) 📄✅ — строит «представления» текста и гоняет по ним те же шаблоны, отображая попадания назад на исходные символы: `worded` (числа словами → цифры), `spelled` («at»/«dot» в e-mail), `dates` (порядковые и словесные даты → ISO), `folded` (снос zero-width и soft hyphen, **отображение кириллических и греческих похожих символов**, NFKC), `joined` (склейка групп цифр), `casefold` (не по умолчанию).

**EntityTrace** (224 строки) 📄✅ — spaCy `en_core_web_lg` 3.8.0 (MIT) на тексте с замаскированными pattern-попаданиями. spaCy не даёт уверенности, поэтому назначаются фиксированные скоры по метке: PERSON 0.88, GPE 0.85, ORG 0.85, LOC 0.74, FAC 0.70. В `balanced` используется **только для мест**; имена — через ensemble fallback.

**ContextGuard** (304 строки) — см. §4.2.

**PIITagger** (452 строки) 📄✅ — токен-классификатор на базе `microsoft/deberta-v3-small` (MIT), обученный **только на сгенерированном тексте** (`bench/tagger/`). Веса — `sherwinvishesh/surrogateshield-pii-tagger`, пин по SHA-256 `f9e5821151ac…`; чужие веса → fail-closed. BIO-теги: PERSON, ORG, STREET, CITY, REGION, POSTCODE, LOCATION, AGE, DATE_OF_BIRTH, EMAIL, PHONE, HANDLE, URL, NETWORK, ID, CREDENTIAL. Окна 256 токенов, шаг 64. **Самый ценный компонент: без него утечка растёт с 0.8 % до 10.8 %** 📄⚠️ (сверено: `no_tagger` = 396/3677 = 10.77 %).

**Structural passes** (1 490 строк) 📄✅ — правила по разметке и формулировкам, а не по отдельным словам: имена после «my name is», титулы, приветствия, метки форм, организации целиком, адрес по частям, колонки CSV, спикеры чата, строки «PAYMENT TO», display names в заголовках писем, отбрасывание неправдоподобных организаций.

**Resolver** (82 строки) 📄✅ — ранг источника: `pattern_scan` → `canonicaliser` → `structural` → `pii_tagger` → `context_guard` → `entity_trace`; затем таблица конфликтов типов (все дефолтные пары — `"score"`); затем наибольший скор.

## 4. Механизмы против контекстных утечек

### 4.1 Relation gate (Pass R) — ключевой механизм

**Это реальный, самый крупный по коду механизм защиты от контекстных утечек: 1 206 строк.** ✅ проверено чтением кода.

**Задача, которую он решает** (дословно из докстринга `relation_gate.py`) ✅:

> «NER tags every proper noun: acronyms («SLA», «W-4»), programming terms («Django», «Python 3.12.4»), greetings («Regards»), public figures («Taylor Swift»), public companies («Nvidia») and places that are only the topic of a question («the population of Tempe»). **The rule the J2 corpus encodes is that an organisation or place is personal only when it is tied to a person.**»

Примеры из докстринга:

| Выражение | Тип | Решение |
|---|---|---|
| «I work at Mercy General» | ORG | **tied → маскируется** |
| «my son goes to Kyrene Middle School» | ORG | **tied → маскируется** |
| «Compare Microsoft, Apple and Nvidia» | ORG | public → остаётся |
| «How far is Tempe from Phoenix?» | GPE | topic → остаётся |
| «Liam is 7 and we live near Reno» | GPE | **tied → маскируется** |

**Как именно решается «место/организация не привязаны к человеку»** — три шага, дословно из документации 📄 (полностью соответствует коду):

1. **Drop the obvious.** Мусорные спаны, публичные лица (из встроенного `public_people.txt`) и обычные слова, прочитанные как имена, отбрасываются.
2. **Look for ties.** Привязкой считается: имя устройства, контекст выданного ID в пределах 60 символов, перволичный маркер до или после («I work at», «we live near», «my doctor»), метка поля, связь с человеком, метка CSV, слот организации, подпись или заголовок e-mail. Выданный ID (карта, банковский номер, IBAN, ID, паспорт или права) в пределах 60 символов в том же предложении тоже привязывает. **Привязки распространяются через людей и через места/организации, которые уже привязаны** (транзитивное замыкание — в коде это цикл `while changed` ✅).
3. **Decide.** Приватные люди маскируются всегда; привязки решают для мест и организаций. Многословные организации с правовой формой маскируются, если не публичны. Публичные организации и нарицательные имена отбрасываются. Привязанные или *vouched* сущности (скор стадии ≥ её `gate_above`) маскируются. **Если в сообщении есть любой якорь** (e-mail, телефон, SSN, DOB, адрес, карта, права, паспорт, ID, банк. номер, IBAN, handle, URL, возраст, credential или имя человека), то **непривязанные места и организации, не являющиеся публичными или нарицательными, тоже маскируются.** Всё остальное уходит как написано с причиной `not_tied_to_person`.

Код подтверждает: константа `_ANCHOR_TYPES` включает `email, phone_intl, phone_us, phone_uk, ssn, dob, address, credit_card, us_driver_license, passport, id_number, us_bank_number, iban, handle, url, age, credential, PERSON`; порог близости `_ANCHOR_REACH = 200` символов, `_NAME_REACH_ACROSS = 80` через пустую строку ✅.

**Отдельный подмеханизм — `impersonal`:** в безличном тексте (60+ слов без первого/второго лица и без идентификатора рядом) имена, места и организации отбрасываются с причиной `impersonal`. Плюс правила `fiction` и `narrative` для художественных текстов ✅.

**Отдельный подмеханизм — `message_language` + `is_foreign_fragment`:** определяет язык сообщения по служебным словам для **de / fr / es / it / pt / nl** (минимум 3 стоп-слова, больше чем английских/Hinglish), и отбрасывает спаны, которые являются частью клаузы, а не именем: «Kannst du diese», «Ele nasceu», «Ruf Sie», «Kündigung» ✅ проверено чтением кода. Это защита от ложных срабатываний английской NER на неанглийском тексте, **не** поддержка других языков.

**КРИТИЧЕСКОЕ НАБЛЮДЕНИЕ, которого нет в документации.** Я посмотрел абляцию `no_gate` в файле результатов: **выключение гейта снижает утечку на injected-слайсе с 0.82 % до 0.65 %** (30 → 24 из 3 677) ✅ проверено. Одновременно гейт **снижает ложные правки**: spurious 612/4405 (13.9 %) против 748/4559 (16.4 %) при выключенном гейте, и **увеличивает долю нетронутых естественных сообщений** с 216 до 232 из 249 негативов/2 153 из 2 433 📄⚠️.

**То есть relation gate — это инструмент борьбы с ложными срабатываниями и сохранения полезности ответа, а не инструмент снижения утечек.** На вставленных «золотых» данных он даже немного вредит: места и организации, которые гейт счёл «не привязанными к человеку», среди вставленных значений оказываются утечкой. Документация этого числа не публикует, хотя файл открыт в репозитории.

### 4.4 Анафора и референция («мама», «та фирма», «последний отчёт») — НЕ решено

**Прямой ответ на главный вопрос: нет, они этого не решают. Это подтверждается отсутствием кода.** ✅ проверено:

- Поиск по всей кодовой базе и документации регулярками `anaphor|corefer|coref|referent|antecedent|co-reference` → **0 совпадений** ❌
- В коде нет никакой модели или эвристики разрешения референтов.
- Что есть по смежной теме: правило `_KIN` понимает **имена после терминов родства** («my sister Anjali» → найдёт *Anjali*), но **не** сам термин «мама» как ссылку на ранее введённую сущность.
- Согласованность суррогатов (`consistency.py`) связывает **повторяющиеся значения**, а не местоимения и указательные обороты: если пользователь один раз написал «Анна Сидорова», а потом «она сказала», второе «она» — не спаны PII вообще и уходит как есть.

**Косвенное подтверждение от самих авторов.** В препринте есть признание структурного ограничения восстановления (ResolvePass), которое является ровно отказом на референциальных формах 📄 дословно:

> «When the LLM reformulates rather than reproduces a surrogate verbatim—paraphrasing "Jonathon Reed" as "Reed" in a context where "Jonathon" does not appear, **the surrogate may persist in the displayed output**. Pass 3's fuzzy matching partially compensates, but **cannot resolve cases where the LLM's reformulation shares no lexical overlap with the surrogate**.»

То есть: если модель заменила фейковое ФИО на референт без лексического пересечения, SurrogateShield не восстановит настоящее значение. Это **ровно тот класс задач**, который в нашей постановке описан как «мама», «та фирма», «последний отчёт».

**И признание на уровне детекции** (из раздела Limitations препринта, дословно 📄):

> «**Explicit versus contextual identity leakage.** SurrogateShield detects and replaces explicit PII: named entities and structured identifiers that match known syntactic patterns. **It does not address contextual or semantic leakage, where identity is implied by non-PII tokens in combination.** A query such as "I am the only radiologist at [regional hospital] and my patient in bay 4 has a rare presentation of…" exposes identity through role, institution, and clinical specificity—no name, SSN, or email address need appear. … We consider the **explicit/contextual boundary a fundamental scope limitation of any NER-based anonymisation approach**.»

## 5. Многоходовые диалоги и восстановление

### 5.1 Сессии и `quoted_back`

**Сессии.** ✅ проверено: состояние PII живёт в объектах `surrogateshield.Session`, по одному на разговор конечного пользователя (`with Session() as s: s.mask(...); s.unmask(...)`; асинхронные близнецы `amask`/`aunmask`). Каждая сессия владеет своим ShadowMap. Дашборд держит **две истории** 📄✅:

- `messages` — то, что видит пользователь: его текст как набран и ответ с восстановленными значениями;
- `api_messages` — то, что **переотправляется**: санитизированный текст и ответ модели как она его написала.

**Провайдеру уходит только `api_messages`.** Это архитектурно важно: история, накапливающаяся у провайдера, состоит исключительно из суррогатов.

**Механизм `quoted_back`** (шаг 15 каскада) — защита от «подстановки подмены в подмену». ✅ проверено в коде:

- `consistency.py:145`: `def quoted_back(mappings: Iterable[str]) -> Set[str]`
- `pipeline.py:2146`: `def _drop_quoted_back(entities, text, skip_values)`
- `pipeline.py:2102–2108`: применяется к `confirmed` и `needs_confirmation`, причина записывается как `"quoted_back"`

**Точное описание** 📄: «A surrogate from an earlier message of the session, **or anything inside one**, is not PII whichever stage found it (reason `quoted_back`), so a message that quotes an answer back gets **no surrogate of a surrogate**.»

То есть: если модель в ответе написала «Adya Nath», а пользователь в следующем сообщении процитировал этот ответ, каскад не примет «Adya Nath» за настоящее имя и не станет придумывать суррогат для суррогата. Без этого механизма цепочка подмен росла бы с каждым ходом и восстановление сломалось бы.

### 5.2 ResolvePass: четыре прохода восстановления

✅ проверено чтением `core/reconstruction/resolve.py` (445 строк) и документации.

**Общее правило:** каждый перезаписанный спан защищён от последующих проходов, и ничего не заменяется внутри более длинного слова или числа.

| Проход | Что сопоставляет | Пример (суррогат → оригинал) |
|---|---|---|
| **1. Exact** | Весь суррогат целиком, сначала самые длинные, без учёта регистра с переносом регистра. Совпадение в нижнем регистре считается только для многословных суррогатов или тех, что содержат цифру/`@` | «ADYA NATH» → «PRIYA RAMAN» |
| **2. Component** | Последовательности 2+ слов из многословного суррогата, сначала длинные, выравниваются пословно с оригиналом (последовательность, разрывающая изменённый блок слов, не используется) | «6237 James» → «412 Alder» (суррогат «6237 James Street, Olympia», оригинал «412 Alder Street, Portland») |

| **4. Name parts** | Имя отдельно (не если следующее слово с заглавной) или фамилия после титула. Только для «человекоподобного» суррогата (2+ слова с заглавной, без слов-организаций) с тем же числом именных слов, что у оригинала, когда часть не встречается в другом отображении и не предшествуется заглавным словом в середине предложения. **С учётом регистра** | «Adya» → «Priya», «Ms. Nath» → «Ms. Raman» |

| Файл | `<storage_dir>/<session_id>.shadowmap`, режим **0600**; каталог принудительно **0700** (`os.makedirs(mode=0o700)`, `os.chmod(0o700)`) |

| Ключ | **HKDF-SHA256**, 32 байта: `ikm` = секрет устройства, `salt` = id хранилища, `info` = `shadowmap-v1` (или `transcript-v1` для транскриптов дашборда) |
| Associated data | `kind \| id` (`aad = kind || b"\|" || id`) — файл, переименованный в другую сессию или другой kind, **не расшифруется** |
| Nonce | 12 свежих случайных байт (`os.urandom(NONCE_SIZE)`) на каждую запись |
| Шифрование | `cryptography`'s `AESGCM` |
| Запись | Атомарная: временный файл → `os.fchmod(fd, 0o600)` → запись → `os.fsync()` → `os.replace()` |
| Повреждённый файл | Переносится в `<name>.corrupt-<unix time>` (никогда не удаляется) и поднимается `CorruptStoreError` |
| Старые файлы | Pre-v1 (без magic, без AAD, info `shadowmap`) ещё читаются и перезаписываются в v1 |

### 6.2 `device.key` — единственный ключ

✅ проверено:

| Свойство | Значение |
|---|---|
| Путь | `$SURROGATESHIELD_HOME/device.key`, по умолчанию `~/.surrogateshield/device.key` |
| Содержимое | **32 случайных байта** (`os.urandom(SECRET_SIZE)`) |
| Режим | **0600** в каталоге **0700** |
| Создание | Атомарно через `os.link(tmp, key_path)` — падает, если файл уже существует, поэтому два одновременно стартующих процесса договариваются об одном секрете |
| Свободные права | Подтягиваются к 0600 с предупреждением `[ShadowMap] <path> had loose permissions; fixed to 0600` |
| Битый ключ | Не ровно 32 байта → `ShadowMapStorageError`; ключи **не** выводятся из усечённого секрета |
| `ALLOW_EPHEMERAL_KEY` | По умолчанию `False`; при `True` процесс использует случайный секрет на время жизни и логирует, что ничего сохранённого не будет читаемо после выхода |

**Честное предупреждение самих авторов** 📄: «**The device secret is the only key.** Anyone who can read `~/.surrogateshield/device.key` and a `.shadowmap` file can read the map. Losing `device.key` makes every stored map and transcript unreadable.» То есть шифрование защищает **at-rest** (украденный файл без ключа), но не даёт защиты от локального противника с доступом к домашнему каталогу пользователя. Это не «zero-knowledge» и не защита от вредоносного кода на машине.

### 6.3 Fail-closed (DetectorUnavailable)

✅ проверено:

- `core/errors.py`: `class DetectorUnavailable(RuntimeError)`
- Более 15 точек `raise DetectorUnavailable` в `pii_tagger.py` (отсутствие весов, несовпадение SHA-256, отсутствие fast-токенизатора, неизвестные метки), плюс в `entity_trace.py` и `context_guard.py`

- Обоснование авторов 📄: «A detector that silently returned nothing would send your data unmasked, so this is deliberate»

Причины и предписанные исправления 📄: отсутствие spaCy/`en_core_web_lg`; сбой spaCy на конкретном вводе; отсутствие `transformers`/`torch` или незакешированный ContextGuard в офлайне; не скачанный tagger или несовпадение SHA-256; незарегистрированный плагин в конфиге.

### 6.4 Прочие меры ✅ проверено (по коду/докá)

```python
def token_half(tok: str) -> str:
    """``eval`` or ``train``, by a keyed hash of the word (half the first byte's range each)."""
    return POOLS[hashlib.sha256(f"{POOL_KEY}:{tok}".encode()).digest()[0] >> 7]
```

Списки слов (имена, фамилии, улицы, города, компании, почтовые провайдеры, слова для паролей) делятся пополам **хешем с ключом**: `eval` — для тестовых идентичностей, `train` — для обучения tagger'а. 1. ✅ Замороженный сплит с хешем и **код, который физически отказывается скорить** без фриза.
2. ✅ **Пререгистрация** десяти гипотез до розыгрыша данных, хеш зафиксирован во фризе.
3. ✅ Публикация **провала test-2 (NO-GO)** без переименования и переоценки.
4. ✅ Разделение train/eval **хешем с ключом** — реализовано, не заявлено.
5. ✅ Все «руки» — реальные библиотеки с пинованными версиями, каждая пишет хеш конфигурации.

8. ✅ Отдельный внешний датасет (Nemotron-PII от NVIDIA), которого авторы не писали.

**Слабые стороны и оговорки:**

1. **Это по-прежнему самоописание.** Ни одна цифра не проверена третьей стороной; препринт с 0 цитирований; лицензия Apache-2.0 позволяет проверить, но никто не проверил.
2. **Injected-слайс — не реальные ПД.** 3 677 значений вставлены генератором в тексты без ПД. Реальные ПД измеряются только на 96 значениях, и там они проигрывают. **Главная цифра «0.8 %» относится к искусственно вставленным значениям, а не к тому, что реально печатают люди.**
3. **Divergence препринт ↔ докá.** Опубликованные в препринте числа (F1 98.87 %, BERTScore 94.85 %) относятся к другой системе и другому корпусу. Ни препринт, ни докá не публикуют числа test-3 в рецензируемом виде.
4. **Найдено мною: сырой `multiturn_realdata_test3.json` содержит `H7''' holds: false`** (потому что критерий межходовой согласованности невозможно измерить — «no gold value recurs across turns»), тогда как `verdict_test3.json` помечает `H7''' holds: true` с подстановкой другого критерия (судья + восстановление). Документация утверждает «All ten checks (every one holds)». Формально подстановка описана в `requirement`, но расхождение между двумя закоммиченными файлами стоит держать в голове.
5. **Судья и атакующий — те же модели Anthropic, что и отвечающий** (отвечает `claude-sonnet-4-6`, судит и атакует `claude-opus-5-5`). Честно, что атакующий сильнее отвечающего, но независимости от вендора нет.
6. **«Живые» тесты (качество ответа, multi-turn, attacker) невоспроизводимы без `ANTHROPIC_API_KEY`** и стоят денег; в файлах есть `calls` с токенами (например, 1 500 вызовов и 1.2 млн выходных токенов на utility) ✅.

### 8.2 Из препринта — раздел 6.2 Limitations (полный, дословные формулировки)

Препринт содержит **гораздо более глубокий** список ограничений, чем документация. Привожу дословно (акцент мой), это самый ценный материал для нашего позиционирования 📄:

> **Detection coverage is finite.** SurrogateShield detects 22 PII types, but no enumeration is complete. Novel identifier formats (medical record numbers, military service numbers, jurisdiction-specific ID schemes), domain-specific structured PII, and **implicitly identifying information, writing style, rare medical conditions, unique professional circumstances, or combinations of apparently innocuous facts**, all remain outside the current detection scope. The quasi-identifier risk detector **partially** addresses this for the ten statistically characterised combinations grounded in Sweeney's work, but **no finite rule set can enumerate the full space of re-identification risk from contextual inference**.

> **Evaluation dataset uses synthetic PII in human-authored query structures.** … **No publicly available corpus of real user LLM queries with ground-truth PII annotations exists**, and for good reason: assembling such a dataset would require collecting and publishing the very sensitive user data this paper is designed to protect. … **Real-world queries may exhibit greater grammatical variability, code-switching, typos, and unconventional PII formatting that could affect detection recall.**

> **Surrogate quality depends on Faker's distributions.** Faker's generators weight toward **common Western names, US address formats, and English-language conventions**. For users with names from **underrepresented linguistic backgrounds**, surrogates may be stylistically inconsistent with the surrounding query context — a discrepancy that could signal to an observer that anonymisation has occurred. Locale-aware surrogate generation, or context-conditioned generation via a local language model, would address this.

> **ResolvePass has an inherent scope restriction.** … **Pass 2 is intentionally scoped to the unresolved surrogate set only** … When the LLM reformulates rather than reproduces a surrogate verbatim — paraphrasing "Jonathon Reed" as "Reed" in a context where "Jonathon" does not appear, **the surrogate may persist in the displayed output**. Pass 3's fuzzy matching partially compensates, but **cannot resolve cases where the LLM's reformulation shares no lexical overlap with the surrogate**.

> **The service-query boundary is heuristic.** The 15-pattern ServiceQueryDetector produces both false positives (personal queries classified as service queries, leading to under-anonymisation) and false negatives (service queries classified as personal, leading to over-anonymisation with reduced answer utility). … A learning-based classifier … would improve precision **at the cost of an additional local model**.

> **Dual-history resume on legacy conversations.** When loading a conversation saved before the dual-history architecture was introduced, the API history (`api_messages`) is empty. … preserving the display history for the user but **losing multi-turn LLM context continuity**.

> **Explicit versus contextual identity leakage.** … **It does not address contextual or semantic leakage, where identity is implied by non-PII tokens in combination.** … Resolving this class of leakage requires a full semantic model of re-identification risk … This is an open research problem … We consider the **explicit/contextual boundary a fundamental scope limitation of any NER-based anonymisation approach**.

### 8.3 Из препринта — 6.3 Future Work (что они сами считают нерешённым)

📄 дословно:

> **Implicit PII detection.** The most significant open problem is PII that takes no form of a named entity or structured identifier. Writing style fingerprinting, topically rare disclosures (specific rare diseases, unique professional roles), and **cross-query linkage attacks in which individually innocuous queries combined narrow the anonymity set** all fall outside the current cascade's detection scope.

> **Context-aware surrogate generation.** MimicGen currently draws surrogates from Faker's fixed distributions **independently of the surrounding query text**. A local language model could generate surrogates conditioned on context.

> **Formal privacy bounds.** The quasi-identifier risk detector provides **heuristic warnings** grounded in Sweeney's empirical estimates, but computes **no formal privacy bound for the full query**.

> **User study for answer quality.** BERTScore measures query-level semantic similarity, **not the quality of the LLM's answer** to a surrogate-substituted query. A controlled user study … would provide the most direct empirical evidence for the utility claim.

### 9.4 Что для других языков всё-таки есть (частичная защита, не поддержка)

Чтобы быть точным, у них есть **несколько мер, полезных для неанглийского текста**, но это защита от ложных срабатываний и качество генерации, а не детекция:

1. **Определение языка сообщения** для `de / fr / es / it / pt / nl` (`message_language()`) и отбрасывание «неименных» спанов (`is_foreign_fragment()`): «Kannst du diese», «Ele nasceu», «Der Vertrag», «Kündigung» ✅ проверено. Это снижает ложные правки на неанглийском, но **не добавляет** находимости ПД.
2. **Кросс-язычные маркеры привязки** в relation gate: `vivo, vive, trabajo, j'habite, travaille, wohne, arbeite, moro, trabalho, abito, lavoro` ✅ проверено.
3. **Титулы на многих языках** (Herr, Frau, Monsieur, professora, dottore, señor…) и служебные слова français/deutsch/nederlands/hinglish ✅.
4. **Суррогаты с сохранением письменности и локали.** `identity.py` содержит `_SCRIPT_LOCALES = {"Cyrl": ("ru_RU",), "Grek": ("el_GR",), "Deva": ("hi_IN",), ...}` ✅ — то есть **генерация** умеет выдать кириллическое имя (Faker `ru_RU`), если кириллическое имя будет обнаружено. Латиница: `en_US, en_GB, en_IN, es_ES, es_MX, fr_FR, de_DE, it_IT, …` ✅.
5. **Сворачивание похожих символов** в canonicaliser: кириллические/греческие визуальные двойники заменяются, NFKC. Но это **антиспуфинг** («рriya@…» с кириллической «р»), а не поддержка русского.
6. **Косвенно: «multilingual» в докá относится только к ключевым словам credential** — и, как я показал, русского среди них нет.

## 11. Что это значит для нашего позиционирования

### 11.1 Наше утверждение № 1: «замена на похожие фейки в науке доказана, а в продуктах не сделана»

**ОПРОВЕРГНУТО — и дважды.**

**Во-первых, «в продуктах не сделана» — неверно.** ✅ проверено: SurrogateShield — работающий продукт с Apache-2.0, опубликованный на PyPI (версия 1.9.0), с Python API, CLI, терминальным дашбордом, 1 432 тестами, шифрованным хранилищем, fail-closed-поведением и сессиями. Мы **не** первые, кто «заменил редакцию на связные фейки в продукте». Это надо принять как факт и убрать из позиционирования формулировку «не сделано».

**Во-вторых, «в науке доказана» — тоже неверно, но по другой причине.** ✅ проверено: публикация — это **препринт arXiv без рецензирования**, с одним автором, **нулём цитирований**, без venue и journal-ref. OpenAlex: `type: preprint`, `is_published: false`, `is_accepted: false`. То есть «доказана в науке» — переоценка: доказательства прошли лишь самоописание и внутреннюю (пусть и добросовестную) методологию. Нет независимого воспроизведения, нет рецензии, нет цитирований.

**Что от нашего утверждения остаётся:** «идея (суррогаты вместо редакции) в литературе **обсуждается**, в одном продукте **реализована**; но ни в одном продукте она не реализована **с русским языком приоритетом № 1** и в **бюджете 250 МБ / 25 мс p95**». Утверждение должно быть переформулировано из «мы первые, кто это делает» в «мы делаем это на русском и в ресурсном бюджете, который никто не достиг».

### 11.2 Наше утверждение № 2: «контекстные утечки не решены нигде»

**ЧАСТИЧНО ОПРОВЕРГНУТО. Требуется разделение на три разных класса задач.**

**Класс A — привязка места/организации к человеку («та фирма», «мы живём рядом с Рино», «я работаю в Halvorsen Dental»). РЕШЕНО у них, инженерно и неглупо.** ✅ проверено чтением 1 206 строк `relation_gate.py`. Это не заглушка и не эвристика на пять строк: транзитивное распространение привязок, 60-символьные окна для выданных ID, правила для художественных и безличных текстов, глоссарий публичных лиц и организаций (`public_people.txt`), кросс-язычные маркеры, определение языка сообщения для 6 языков, защита от «persona»-фреймов («you are now …»). Наш тезис «контекстные утечки не решены нигде» **в этой части неверен**. Более того, механизм работает в правильную сторону: он **снижает ложные правки** и повышает долю нетронутых естественных сообщений.

**Но с двумя важными оговорками, которые дают нам позицию:**
- Метрика гейта **не опубликована авторами**: в документации нет числа, показывающего его вклад. Я нашёл его в открытых файлах результатов: **гейт увеличивает утечку на injected-слайсе** (0.82 % против 0.65 % без него). То есть это инструмент **полезности и FP**, а не приватности. Мы можем показать, что их собственный «главный механизм против контекстных утечек» не улучшает приватность на их же данных.
- Механизм — **правила и списки**, без вероятностей и без формальных гарантий. Сами авторы: «computes **no formal privacy bound** for the full query» 📄.

**Класс B — семантические/контекстные утечки (роль + учреждение + редкая специфика: «единственный радиолог в [больнице], у пациента в 4-м боксе редкая картина»). НЕ РЕШЕНО, и авторы прямо говорят, что это фундаментально.** 📄 дословно: «It does not address contextual or semantic leakage, where identity is implied by non-PII tokens in combination… We consider the explicit/contextual boundary a **fundamental scope limitation of any NER-based anonymisation approach**». **Здесь наше утверждение подтверждается, но с важной поправкой: это не «никто не озаботился», а «признано открытой проблемой с указанием, почему NER-подход её не решает».** Значит, наше преимущество должно быть архитектурным (не NER-центричный подход), а не «мы тоже заметили проблему».

**Класс C — анафора и референция («мама», «та фирма», «последний отчёт») как ссылки на защищаемую сущность. НЕ РЕШЕНО и, судя по коду, даже не поставлено как задача.** ✅ проверено: 0 совпадений по `anaphor|corefer|referent|antecedent` во всей кодовой базе и документации. Косвенное подтверждение — их собственное признание в Limitations препринта про «Jonathon Reed» → «Reed»: восстановление не работает, когда переформулировка модели не пересекается лексически с суррогатом. **Это самая чистая ниша из трёх.** Ни в документации, ни в препринте, ни в будущих работах нет пункта про разрешение референтов — единственный пункт про «Implicit PII detection» говорит про стилометрию, редкие болезни и cross-query linkage, но **не** про анафору.

**Итоговая переформулировка нашего тезиса.** Вместо «контекстные утечки не решены нигде» следует говорить:

> «Контекстная привязка "место/организация → человек" решена эвристиками в SurrogateShield, но ценой утечек на их же данных (0.82 % против 0.65 % при выключенном механизме), без формальных гарантий и только для английского. Семантические утечки (роль + учреждение + редкая специфика) признаны открытой проблемой самими авторами. **Анафора и референция на защищаемые сущности ("мама", "та фирма", "последний отчёт") не реализованы вообще — ни в коде, ни в планах.**»

Это честнее, проверяемо и не даёт конкуренту возможности опровергнуть нас их же файлами.

### 11.4 Новые риски для нашего плана, которые надо учесть

1. **Лицензионный риск переиспользования.** Код Apache-2.0 — можно изучать и заимствовать идеи (с указанием). Модели — MIT/Apache-2.0, но **веса надо указывать отдельно** (565 МБ, MIT). Прямое заимствование кода не даёт нам русского языка, но даёт нам их ошибки.

## 12. Что стоит перенять (список)

Отсортировано по отношению «польза / стоимость внедрения».

### Методология бенчмарка (перенять в первую очередь — это их самое сильное)

1. **Замороженный сплит с физическим отказом скорить.** Не «мы не подсматривали», а код, который падает без `FREEZE.json` и без совпадения хеша пререгистрации. `check_freeze()` в `score.py` — эталон.
2. **Пререгистрация гипотез до розыгрыша данных.** Файл `HYPOTHESES_TEST3.md`: десять гипотез H1'''…H10''' с явными порогами, хеш зафиксирован во фризе, правило вердикта `decide` не меняется. Скопировать структуру.
3. **Публикация провала без переименования.** Их test-2 = NO-GO, и это осталось в файлах навсегда. Нам нужна такая же норма: провал фазы публикуется как провал.
4. **Разделение train/eval ключевым хешем.** `token_half(tok) = sha256(f"{KEY}:{tok}").digest()[0] >> 7` — гениально просто: гарантирует, что ни одно слово из теста не встречалось при обучении, без ручного управления списками. Применимо к нашему русскому словарю имён/улиц/городов.
5. **Жёсткое и однозначное правило метрики.** «Значение считается утёкшим, если любая буква или цифра осталась неотредактированной или скопирована в суррогат; полумаскированное = утечка». Никаких «частично защищён».
6. **Пер-«рука» хеш конфигурации + отказ при смешивании хешей.** Позволяет доказать, что все сравниваемые конфигурации зафиксированы.
7. **Хеш коммита кода детектора во фризе** + проверка, что код не разошёлся после фриза.
8. **Слайс-структура бенчмарка:** injected (вставленные известные значения) + natural (реальный текст) + odd-format (необычные форматы) + внешний датасет. Каждый слайс измеряет своё. **И обязательно: не смешивать «0.8 % на вставленном» с «30 % на реальном».**
9. **Внешний датасет, которого мы не писали,** как вторая проверка (у них — Nemotron-PII от NVIDIA).
10. **Атака сильной моделью** как метрика приватности: не «мы замаскировали», а «что модель смогла восстановить побуквенно», с подсчётом отдельно тех частей, что суррогаты сохраняют намеренно.
11. **BERTScore против ответа на исходный промпт** + слепой судья **и публикация незначимых интервалов** (у них CI судьи против GLiNER содержит 0 — и они это пишут).
12. **Абляции по каждому компоненту** с указанием вклада (у них: tagger 10.8 %, canonicaliser 3.9 %, regex 1.4 %, всё вместе 15.7 %, все регулярки сломаны 26.1 %).

### Архитектура и безопасность

13. **Fail-closed как принцип.** `DetectorUnavailable` — если стадия не может работать, ничего не маскируется и **ничего не отправляется**. Лучше отказ, чем молчаливая отправка незамаскированного текста.
14. **AES-256-GCM + HKDF per-store ключ + associated data `kind|id`.** У них: `SSv1 || nonce(12) || AESGCM(...)`, ключ = HKDF-SHA256(device secret, salt=id, info=kind), aad = `kind|id`. Это мешает переименовать файл в другую сессию. Реализация на ~430 строк, полностью переносимая идея.
15. **`device.key`: 32 байта, 0600, атомарное создание через `os.link`,** подтягивание свободных прав с предупреждением. Модель угроз и **честное признание**, что это защита at-rest, а не от локального противника.
16. **Атомарная запись приватных файлов** (tmp → chmod 0600 → write → fsync → replace).
17. **Повреждённый файл не удаляется, а переносится** в `.corrupt-<time>` с исключением. Никогда не превращать нечитаемую карту в пустую (иначе ответы останутся невосстановленными).
18. **Две истории: `messages` (для пользователя, с оригиналами) и `api_messages` (только суррогаты, уходит провайдеру).** Провайдер никогда не видит накопленную историю с оригиналами.
19. **Режимы адреса `auto` / `shift` / `replace` / `coarse`.** Идея «сдвинуть номер дома на ±1, а улицу и город оставить» для сервисных запросов («аптеки рядом») — умное решение конфликта «полезность ответа vs приватность». И **`coarse` для чувствительных тем**: улица → «my area», ZIP убирается, город остаётся.
20. **Resolver с рангами источников** (regex → canonicaliser → structural → tagger → context_guard → spaCy) и таблицей конфликтов типов. Простое и объяснимое правило вместо «модель решит».
21. **Canonicaliser как «представления» текста** (worded / spelled / dates / folded / joined) с отображением попаданий назад на исходные символы. Изящно решает «four one five five five…» и «name at domain dot com».
22. **Парные суррогаты вместо независимых:** e-mail, handle и ФИО указывают на одного фейка; локальная часть e-mail перестраивается в том же стиле; `+tag` сохраняется; бесплатные домены сохраняются. Проверки: карта проходит Luhn с теми же первыми двумя цифрами; IBAN с той же страной и валидным mod-97; телефон с тем же кодом страны, транк-префиксом и разделителями.
23. **Consistency по сессии + защита от коллизий:** суррогат никогда не равен оригиналу, не содержит оригинал как целое значение, не совпадает с уже имеющимся в сообщении текстом; до 20 попыток, затем `RuntimeError` вместо «сомнительного» суррогата.
24. **`quoted_back`:** суррогат (и всё внутри него) из предыдущего сообщения сессии не считается PII, чтобы не появился «суррогат суррогата».
25. **Структурные проходы по разметке** (метки полей, колонки CSV, спикеры чата, подписи, display names, «PAYMENT TO», имена устройств с именем владельца, JSON-поля) — большой практический выигрыш на реальных текстах.
26. **Public-people / public-org глоссарии** — чтобы не маскировать «Taylor Swift» и «Microsoft» в топических вопросах.
27. **Quasi-identifier предупреждения** — как минимум UI-уровень: показать пользователю риск «ZIP + DOB + пол». У них это только информация, но как UX-элемент идея хорошая. **Не называть это «скорингом», если у нас будет таблица.**
28. **DetectionConfig как объект с SHA-256-хешем и пресетами** (`balanced` / `strict` / `fast` / `classic`) — результат всегда можно связать с точной конфигурацией.
29. **`gate_above` / vouch-механизм:** детектор с высокой уверенностью может «поручиться» за сущность и пропустить её через гейт без привязки.

### Инженерные практики

30. **Один источник реализации для библиотеки и приложения:** дашборд импортирует библиотеку, а не имеет своей копии детекции/генерации/восстановления. Отдельный тест на паритет.
31. **`DetectorUnavailable` с указанием, что именно установить** — сообщение об ошибке называет пакет/модель и команду.
32. **Плагины детекторов** через реестр (`register_detector`) с маршрутизацией по `type_sources` — расширяемость без правки каскада.
33. **Проверка перед отправкой** (`SendMismatch`): пересчитать ожидаемый текст и упасть, если он расходится с отправляемым. Защита от регрессий, приводящих к утечке.
34. **CI с порогом покрытия** (`--cov-fail-under=85` на ядре).
