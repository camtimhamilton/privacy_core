# Сверка контрольных сумм: что подтверждено, что опровергнуто

**Фаза:** 0 (аудит)
**Дата:** 2026-10-16
**Метод:** воспроизводимый скрипт [`verify_checksums.py`](verify_checksums.py), только стандартная библиотека Python
**Зачем:** в плане форматные детекторы РФ объявлены главным отличием №1 и описаны как дающие «высокую точность при нуле ложных срабатываний» (раздел 3 плана). Контрольные суммы должны быть подтверждены на живых данных до того, как на них будет построен детектор.

## 2. Расчётный счёт: алгоритм и доказательство

**Алгоритм**, подтверждённый на живых реквизитах:

1. **Разряды 1–3** — условный номер РКЦ: разряды 5–6 БИК, дополненные слева нулём. Практически для 9-значного БИК это три последние цифры.
2. **Разряды 4–23** — номер лицевого счёта (20 цифр).
3. Каждая цифра умножается на вес по кругу **7, 1, 3**; берутся **младшие разряды** произведений; их сумма должна быть **кратна 10**.

**Первоисточник.** [Положение Банка России 1417-У](https://www.cbr.ru/Content/Document/File/48858/1417-u.pdf) задаёт порядок нумерации лицевых счетов; сам алгоритм контрольного ключа разобран с примерами в учебном пособии КФУ ([«Банковский практикум»](https://kpfu.ru/portal/docs/F2111974756/B1.V.DV.7.2..Bankovskij.praktikum.pdf), тема 3, страницы 21–22; PDF отдаёт 200, но разделы с таблицами весов в нём не извлекаются текстом — они свёрстаны как изображения).

**Доказательство работоспособности — живой документ, не учебник.** В публичном платёжном документе ООО «ОнЛайм» ([PDF](http://www.onlime.ru/docs/OnLime-Kvitancia_BRF.pdf)) указаны реквизиты: БИК `044525225`, расчётный счёт `40702810638180003655`. Правило выполняется:

```
цифры : 2 2 5 | 4 0 7 0 2 8 1 0 6 3 8 1 8 0 0 0 3 6 5 5
веса  : 7 1 3 | 7 1 3 7 1 3 7 1 3 7 1 3 7 1 3 7 1 3 7 1 3
мл.разр.: 4 2 5 8 0 1 0 2 4 7 0 8 0 0 0 0 1 8 5 5
сумма младших разрядов = 60  ->  60 mod 10 = 0  ->  ключ верен
```

Ключ счёта — 9-я цифра, то есть `6` в позиции `40702810**6**…`. Обратная проверка «сумма при K=0 → ключ» даёт то же значение, что и в документе, — это независимое подтверждение, что веса и порядок разрядов верны, а не подогнаны.

## 3. Дефект в учебнике КФУ (важно для будущих сверок)

Учебник даёт два примера и в обоих подставляет один и тот же префикс **«005»**:

| Пример | БИК из условия | Префикс из БИК | Проходит? | Префикс «005» из текста | Проходит? |
|---|---|---|---|---|---|
| `30101810800000000746` | `049805000` | `000` | нет | `005` | да |
| `40102810100000010001` | `040305000` | `000` | нет | `005` | да |

Оба примера сходятся **только** при префиксе `005`, хотя у обоих указанных БИК хвост `000`. Один и тот же префикс у двух разных БИК — признак типографской ошибки, а не разных алгоритмов. Дополнительно: в примере 1 текст утверждает, что сумма младших разрядов равна «36», тогда как его же собственный ряд произведений даёт **90** (обе суммы кратны 10, но первая арифметически неверна).

**Следствие для работы:** учебная литература по этой теме содержит ошибки и как источник контрольных сумм не годится. Сверять только на живых реквизитах из официальных документов. Этот вывод применён и к остальным типам: всё, что не подтверждено живым примером, помечено как непроверенное.

## 4. Корреспондентские счета — исключение для детектора

Реальный корсчёт `30101810400000000225` (БИК `044525225`) **не проходит** правило ни с одним из 1000 возможных префиксов, при которых проверка вообще может сработать. Значит, корсчета либо нумеруются по иному правилу, либо контрольный ключ там считается с участием условного номера кредитной организации (разряды 7–9 БИК), чего в доступных источниках нет.

**Что это значит практически.** Детектор не должен пытаться валидировать корсчета. Для счёта клиента контрольная сумма работает, для корсчёта — нет, и делать вид, что работает, — это ложная уверенность. В реестре типов счёт остаётся с оговоркой: только лицевые счета клиентов.

## 5. Ложное прохождение: счёт требует контекста

Замер на 200 000 случайных строк (seed фиксирован в скрипте):

| Условие | Доля прохождений |
|---|---|
| 20 случайных цифр, префикс неизвестен | **9.99%** (1 в 10.0) |
| Реалистичное начало счёта `40702…`, префикс неизвестен | **10.02%** (1 в 10.0) |

Причина ровно 10%: проверка сводится к кратности суммы десяти, то есть срабатывает на каждом десятом наборе. Знание БИК это не меняет — оно лишь сужает множество, потому что префикс РКЦ входит в сумму.

**Вывод для детектора.** Счёт из 20 цифр в тексте имеет смысл подменять только при наличии контекста: БИК рядом, метка «счёт»/«р/с», позиция в блоке реквизитов. Один контрольный ключ доказательством не является. Это тот же вывод, что и для ОГРН, ОГРНИП и карт, — и он окончательно закрывает формулировку «ноль ложных срабатываний».

## 6. Что осталось не проверенным

| Пункт | Почему | Что нужно |
|---|---|---|
| ИИН и БИН Казахстана | Не найдено живых примеров с известной контрольной цифрой; алгоритм из вторичных источников | Официальный документ либо реквизиты казахстанской организации |
| УНП Беларуси | То же | То же |
| Веса для расчётного счёта в нормативном тексте | Положение 1417-У по прямой ссылке отдаёт 404; разделы с весами в учебнике свёрстаны картинками | Найти действующую редакцию положения или официальную методику ЦБ |
| Корсчета | Правило не найдено | Отдельный поиск; до тех пор — исключить тип |

Правило проекта: тип с непроверенной контрольной суммой в релизе **не подменяется**. Ложная полнота хуже пропуска, потому что её не видно.

## 7. Воспроизведение

```
python3 phase-0/06-method/verify_checksums.py
```

Скрипт печатает три блока: живые реквизиты, разбор учебных примеров, замер ложных прохождений. Все числа в этом отчёте получены его запуском.
