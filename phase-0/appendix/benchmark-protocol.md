# Протокол бенчмарка privacy-core

**Версия протокола:** 0.1 (черновик фазы 0)
**Статус:** проектируется до детекторов — сознательно, см. раздел 1
**Дата:** 2026-10-16

---

## 1. Зачем протокол существует раньше кода

Порядок работы в проекте отличается от обычного. Протокол пишется в фазе 0, детекторы — в фазе 2, стенд — в фазе 3. Причина в том, что бенчмарк — главный актив проекта, а не побочный продукт. Если протокол появится после цифр, возникнет соблазн подогнать его под результат.

Дополнительная причина обнаружилась в ходе аудита: у конкурента [SurrogateShield](https://github.com/sherwinvishesh/SurrogateShield) уже есть продуманный бенчмарк `test-3` с защитой от подгонки. Если мы придём в фазу 4 со своим протоколом, несовместимым с их, числа окажутся несравнимыми, и весь смысл сравнения пропадёт.

## 2. Принципы

1. **Инвариант важнее процента.** Проверка «наружу не ушло ничего» — это да или нет. Полнота 99% при одной утечке — это провал Core, а не «почти хорошо».
2. **Среднее по типам не считается.** Полнота публикуется по каждому типу отдельно. Среднее скрывает провалы на редких типах, а редкие типы — это паспорта и счета.
3. **Чистый корпус обязателен.** Без текстов без персональных данных невозможно измерить ложные срабатывания, а без них высокая полнота достигается подменой всего подряд.
4. **Разработка и оценка разделены.** Набор, на котором тюнили детекторы, не может использоваться для публикации.
5. **Публикуются и проигранные метрики.** Решение, которое нигде не проиграло, обычно означает, что измеряли не то.
6. **Модель противника описывается.** Результат атаки без указания, кто атаковал и с какими возможностями, — не результат.

## 3. Три уровня

| Уровень | Что проверяет | Проходимость | Роль |
|---|---|---|---|
| **Core** | Инварианты I1–I6, I9 | Должны проходить почти все серьёзные решения | Порог входа в таблицу |
| **Extended** | Полнота, точность, сохранение смысла, ресурсы | Соревновательный | Основная таблица |
| **Adversarial** | Атаки восстановления и деанонимизации | Отдельный отчёт, не порог | Научная часть и честность |

Правило публикации: если Core не пройден, решение попадает в раздел «не прошли порог» с указанием нарушенного пункта. Хорошие числа Extended этого не маскируют.

## 4. Уровень Core: проверки

Все проверки выполняются на замороженном регрессионном наборе. Формулировки инвариантов — в [рабочем документе](../../docs/00-charter.md#3-инварианты-ядра).

| ID | Проверка | Критерий | Как проверяется |
|---|---|---|---|
| C1 | Утечка исходных значений в наружном тексте | 0 | Сравнение наружного текста с исходными спанами по всем нормализациям: регистр, пробелы, дефисы, транслит, гомоглифы, цифры словами |
| C2 | Накопление в истории диалога | 0 | Сессии до 20 реплик; значение из реплики 1 не должно появиться в наружном тексте реплики 5 |
| C3 | Искажение постороннего текста при восстановлении | 0 | Набор ответов-приманок: подмена встречается в чуждом контексте, восстановление её не трогает |
| C4 | Поведение при сбое | Наружу не уходит исходный текст | Инъекция 8 сценариев сбоя: падение детектора, таймаут модели, битая карта, обрыв потока и другие |
| C5 | Согласованность подмен в сессии | Нет коллизий и расщеплений | Сессия с однотипными сущностями: два тёзки, два ИНН с общим префиксом |
| C6 | Обратимость без детектора | 100% | Восстановление по карте при принудительно отключённых детекторах |
| C7 | Хранение карты | Открытый текст отсутствует в файле | Побайтовый поиск исходных значений в файле карты и в логах |

**Что Core не проверяет.** Инварианты I7 (композиция политик) и I8 (контракт профиля задержки) — это свойства библиотеки, а не текста. Они проверяются своими механизмами: I7 — property-based тестом на решётке политик, I8 — замером задержки в CI. Провал любого из них блокирует релиз наравне с C1.

## 5. Уровень Extended: метрики

| Метрика | Определение | Единица | Направление |
|---|---|---|---|
| Recall по типу | Найденные сущности типа / все сущности типа в наборе | доля 0–1 | больше |
| Precision по типу | Верные среди найденных того же типа | доля 0–1 | больше |
| **FP(clean)** | Доля чистых документов, где тип сработал ложно | доля 0–1 | меньше |
| Доля запросов с утечкой | Запросы, где хотя бы одно исходное значение ушло наружу, / все запросы | доля 0–1 | меньше |
| Доля невосстановленных подмен | Невосстановленные подмены / все подмены | доля 0–1 | меньше |
| Сохранение смысла | Сходство ответа на обезличенный запрос с ответом на исходный | BERTScore либо ручная оценка | больше |
| Задержка p50 / p95 | На CPU, текст 2000 токенов, по профилям | мс | меньше |
| Память RSS | Пиковая, по профилям | МБ | меньше |
| Время холодного старта | От запуска до готовности обработать запрос | мс | меньше |
| Размер WASM | Сжатый | КБ | меньше |
| F1 по типам (для сравнения) | Гармоническое среднее precision и recall | доля 0–1 | больше |

Почему последняя метрика отдельно: конкуренты публикуют F1 и почти не публикуют FP(clean). Без неё F1 98.87% ничего не говорит о том, сколько безобидного текста система испортила.

### 5.1 Обязательная поправка: метрика должна быть субъект-уровневой

**[добавлено по итогам фазы 0]** Спановый recall и F1 **систематически обманывают**. Работа SPIA (ACL 2026) показала: при маскировании более 90% явных спанов защита **на уровне субъекта** падает до **33%**. Причина в том, что субъект опознаётся по совокупности оставшегося контекста, а не по отдельным значениям.

Поэтому к метрикам выше добавляются две обязательные:

| Метрика | Определение | Направление |
|---|---|---|
| **CPR** — доля корректно защищённых субъектов | Доля персон, про которых атакующий не смог восстановить ни одного скрытого атрибута | больше |
| **IPR** — доля повторно идентифицированных персон | Доля персон, которых атакующий связал с реальным человеком | меньше |

Публикация только спановых метрик **не допускается**. Это прямое следствие того, что «recall ≥ 0.95» может сочетаться с защитой на уровне субъекта в 33%.

### 5.2 Разбивка по длине диалога обязательна

Утечка растёт с длиной диалога: по данным CIMemories Dialogue — **до 3 раз** при переходе с 1 на 6 ходов. Значит, метрики публикуются отдельно для 1, 3 и 6 ходов, а сводное число по диалогам не заменяет разбивку.

### 5.3 Тест «наш фейк против нашего пропуска»

Суррогаты создают **атакуемую поверхность**: атака Parrot находит **68%** утечек при случайном угадывании 8%. Если детектор пропустил значение, а рядом стоит подмена, сам факт подмены указывает атакующему, где искать.

Отсюда обязательный тест: для каждого пропуска детекции проверяется, становится ли он заметнее из-за наличия подмен в том же тексте. Метрика — прирост успеха атакующего за счёт подмен.

### 5.4 Статистика: не только p-value

При сравнении своего решения с чужим используется **TOST** (two one-sided tests) с заранее объявленным порогом эквивалентности, а не проверка на различие по p-value. Причина: нам нужно уметь заявлять «не хуже», а p-value этого не позволяет. Формат взят из протокола Surrogate Substitution (2026).

### 5.5 Паспорт подмены

Для каждой подмены проверяется не только формат, но и **отсутствие совпадения с реальной сущностью**. Для российских реквизитов это критично: ИНН и ОГРН — публичные реестровые номера, и валидная контрольная сумма **не означает**, что номер вымышленный. Отдельная метрика: доля подмен, попавших в реальные реестры.

## 6. Набор данных

### 6.1 Состав

| Часть | Назначение | Требования |
|---|---|---|
| `dev` | Разработка и тюнинг детекторов | Может меняться в ходе работы |
| `test` | Публикация результатов | Заморожен, версионирован, хэш зафиксирован |
| `clean` | Замер FP(clean) | Тексты без персональных данных: документация, статьи, логи, таблицы |
| `dialogue` | Проверка C2 и контекстных утечек | Многоходовые сессии, включая ссылки («мама», «та фирма») |
| `adversarial` | Атаки | Синтетические персоны с известными комбинациями признаков |

### 6.2 Требования честности

Перенято у `test-3` проекта SurrogateShield и дополнено:

1. **Замороженный хэш.** Скорер отказывается оценивать `test` без совпадения хэша. Изменение набора — новая версия протокола, старые результаты остаются с пометкой версии.
2. **Разделение по словарям, а не только по строкам.** Имена, улицы, названия компаний в `test` не должны встречаться в `dev`. Разделение ключевым хэшем, чтобы нельзя было подобрать.
3. **Пересечение проверяется по документам.** Два документа из `dev` и `test` не должны быть соседними абзацами одного источника — иначе утечка через контекст.
4. **Синтетические значения, реальные носители.** Значения генерируются локально, вставляются в реальные тексты точными правками. Скорер точно знает, что нужно было скрыть. Генератор не придумывает значения «по месту».
5. **Цифры — случайные выборки.** Структурные слова (улица, месяц) могут повторяться, числовые значения — нет.
6. **Слайс необычных форматов.** Телефон словами, почта «имя собака домен точка ру», дата прописью, счёт с пробелами — проверяет, читает ли система смысл или только шаблон.
7. **Слайс безобидных текстов.** Прямой аналог FP(clean): сколько ненужных правок система внесла.

### 6.3 Русский язык

Обязательная база — русский. Английский — дополнительный. Причина: у всех существующих решений английский первичен, у SurrogateShield русского нет вообще.

Требуемые типы для v0.1 (из [реестра типов](../../docs/20-entity-registry.md)): ИНН (юрлицо и физлицо), СНИЛС, ОГРН, ОГРНИП, паспорт РФ, расчётный счёт, БИК, телефон, почта, ФИО, адрес.

**Открытый вопрос фазы 0:** существуют ли открытые русские наборы с реальными типами персональных данных (не только имена и организации). Если нет — набор придётся строить с нуля, и это надо заложить в сроки фазы 3.

## 7. Уровень Adversarial

| Атака | Что моделируется | Метрика |
|---|---|---|
| Прямой вопрос | «Назови настоящее имя собеседника» | Доля успешных извлечений |
| Комбинация признаков | Три безобидных признака вместе идентифицируют человека | Доля успешных идентификаций |
| Инверсия фейка | Существует ли валидный ИНН, подставленный как фейк, в реальных реестрах | Доля фейков, попадающих в реестры |
| Через историю | Данные из реплики 1 извлекаются в реплике 5 | Доля успехов |
| Через формат | Восстановление по формату подмены без карты | Обратимость фейка без карты |
| Запрос цитаты | Просьба повторить ответ дословно, чтобы вытащить подмены | Доля успехов |

**Требование к описанию противника.** Для каждой атаки фиксируется: какая модель атакует, её версия, промпт, число попыток, что считается успехом. Атака без этого — не результат.

Ориентир: SurrogateShield в своей документации приводит 1.8% значений, которые атакующая модель знает точно (против 12.6% у GLiNER-PII и 34.2% у Presidio). Это та планка, которую надо измерять по сопоставимому протоколу.

## 9. Абляции

Обязательная часть отчёта: по одному убирается каждая стадия каскада и публикуется, как меняется доля утечек. Без абляций нельзя понять, что именно работает.

| Что убрано | Ожидаемый эффект |
|---|---|
| Форматные правила | Рост утечек по типам с контрольной суммой |
| Контекстный каскад | Рост FP(clean) |
| Статистический NER | Пропадают ФИО и адреса |
| Модуль контекстных ссылок | Рост утечек на истории диалога |

Ориентир по форме: у SurrogateShield опубликовано, что удаление их PII-теггера поднимает утечку с 0.8% до 10.8%, а поломка всех регулярных выражений — до 26.1%. Такой формат делает отчёт убедительным.

## 10. Воспроизводимость

1. Одна команда прогоняет весь протокол и кладёт результат в JSON.
2. Каждый результат в таблице ссылается на файл результата, коммит и хэш конфигурации.
3. Оффлайн-проверки не делают сетевых вызовов; те, что делают (атаки, оценка смысла), помечены явно.
4. Замеры задержки выполняются на фиксированной конфигурации CPU, которая описывается в отчёте. Без указания машины задержка не сравнивается.
5. Каждый результат сопровождается версией протокола.
